# 第 4 条方案：决策流水线广播 / 订阅架构

> 用户原话（2026-11-24）：
> 「开仓决策像一个流水线广播，不关心下游，有就产出！有一个下单订阅方，去做真实下单！
> 下不下单有一些拦截比如仓位、刚才说的手工单之类的，如果拦截通过，就走下单！
> 有了持仓单之后，就发出信号，也像广播，那么K线演化等出场、止盈、止损等都有了勾子，
> 就运转起来了！没有持仓这些都没意义！你看全部都是灵活的，基于广播订阅的模式！
> 这样的话，你人工仓还一定要基于结构失效的判断吗？每一根K线都有话说，
> 然后判断可以出场了！K线演化即辅助入场也辅助下游」
>
> 本文只出方案，**未改任何代码**。

## 0. 一句话结论

用户描述的架构，**零件在这个仓库里基本都有，缺的是接线**。真正要做的不是新建一套事件框架，
而是把三条现存流水线（决策 / 执行 / 持仓管理）解开耦合，让它们通过一个已有的 `Hub` 说话。

同时必须接受一个代价：这会动到全系统最核心的 `_step`，属于**高风险重构**，
不能和策略调整混在一起做。

2. `kline_intent.py` 的模块注释明确写着「**辅助下单与离场，不是决策者**」，
   并且和 `position_guard.decide(kline=)` 有字段契约（有测试 `test_kline_intent.py:182` 守着）。
   也就是说：**这两块是为彼此设计的，但生产链路一次都没把它们接起来。**

所以第 4 条不是"造新东西"，是"把已经写好、已经测过、却从来没进过生产的东西接上"。

## 2. 现在为什么是这副样子（根因，不是借口）

`_step`（`engine.py:1427`）干了六件事：

```
伦理序：_watch_executor_halt → equity → 记权益 → 对账 → 人工仓出场 → 策略分派
分派：  _is_chan() → _step_trend
        _is_pending() → _step_pending
        adopted_pos and not pos → 只挡开仓，return
        self.pos → _manage（出场）
        无仓 → 算 feats → 评估开仓 → _open（下单）
```

问题不在顺序，在**同一根 K 线的处理被切成了互斥分支**。后果：

- 策略 A 的持仓只能被策略 A 的出场规则管。这正是 11-24 事故的成因：
  `strategy=pending` 的接管仓没有任何正当管理路径（`_step` 里 `if self._is_pending(): return`
  之后 `_step_trend` 那段熔断判断永远不跑）。我上一轮打的补丁
  （`_step` 里插一段 `if self._is_adopted() and not self._is_pending(): _step_adopted_exit(...)`）
  **是对的，但它是一个补丁**：它的存在本身就说明「出场管理按策略分流」这个结构是错的。
- 出场规则每个策略各写一份。`_manage`（剥头皮）、`_step_trend`（趋势）、
  `_step_adopted_exit`（人工仓）、`_pending_close`（挂单仓）—— 四份实现，
  上一轮的 fee 口径分家就是同一个病根：**四份实现必然漂移**。
- 决策写入和下单成功绑在一起。这就是为什么上线前 11-24 全天只有 1 条决策行 ——
  决策流的密度取决于"有没有下单"，而不是"有没有决策"。

## 3. 目标架构（按用户原话逐条落地）

```
                    ┌──────────────────────────────────────────┐
   K线/行情 ───────► │  Hub（复用 feed.py:32，新增事件类型）      │
   (已存在)          └───────────────┬──────────────────────────┘
                                     │ publish(bar_closed)
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
     ┌────────────────┐   ┌──────────────────┐   ┌──────────────────┐
     │ 决策者(多个)     │   │ 持仓管理者(1)     │   │ 观测者(看板/决策流)│
     │ 每根K先说话      │   │ position_guard   │   │ 只读，不产生动作    │
     │ 不关心下游       │   │ decide() P0→P5   │   └──────────────────┘
     └───────┬────────┘   └────────┬─────────┘
             │ publish(intent)     │ publish(exit_intent)
             ▼                     ▼
     ┌──────────────────────────────────────────┐
     │ 执行订阅方 Executor（唯一的下单出口）        │
     │  拦截链：仓位闸 → 手工仓 → 熔断 → 去重      │
     │  t	通过 → 真下单；不通过 → 落一条决策(带原因)│
     └───────────────────┬──────────────────────┘
                         │ publish(fill / position_opened / position_closed)
                         ▼
                 持仓状态成为事件，下游订阅者被唤醒
```

### 3.1 事件词汇表（先定契约，这是全案的地基）

新建 `ai_trader/trading/events.py`，只放数据类，不放逻辑：

```python
@dataclass(frozen=True)
class BarClosed:        # 已有：feed.hub.publish({"type": "bar", "closed": True, ...})
    interval_ms: int; ts: int; o: float; h: float; l: float; c: float; v: float

@dataclass(frozen=True)
class EntryIntent:      # 决策者的产出（"有就产出"，不关心有没有人接）
    strategy: str; side: str; entry: float; stop: float; target: float
    qty_hint: float; reason: str; evidence: dict; bar_ts: int

@dataclass(frozen=True)
class ExitIntent:       # 持仓管理者的产出
    slot: str           # "system" | "adopted"   ← 上一轮拆仓的结果，这里必须原样带上
    action: str         # EXIT_STOP / EXIT_STRUCTURE / PARTIAL_TP / REDUCE / MOVE_STOP
    close_qty: float; new_stop: float; reason: str; evidence: dict

@dataclass(frozen=True)
class PositionOpened / PositionClosed / OrderRejected
```

**要点**：`EntryIntent` 必须能被"无人订阅"时安全落地 —— 只落一条决策行，
不抛异常、不阻塞。这正是"不关心下游"的技术含义。

### 3.2 执行订阅方（唯一的 `place_order` 出口）

新建 `ai_trader/trading/executor.py`（注意：这个名字和现有 `self.ex` 执行器冲突，
实际命名建议 `order_router.py`，见 §7 的命名风险）。

```
on_entry_intent(intent):
    1. 仓位闸：sizing.plan_position() → 名义/保证金/R/liq_buffer   [已有]
    2. 手工仓闸：adopted_pos 存在 → 拒绝，落决策(action=pending_suppressed)  [上一轮已有]
    3. 硬熔断/连亏/权益过期闸 → 拒绝，落决策(gates=[...])          [已有]
    4. 去重：同一 bar_ts 同一 strategy 只执行一次                  [新增]
    5. 通过 → place_order / market_order → publish(PositionOpened)
```

**这一层的关键收益**：所有拦截从"散在调用链上"变成**一条有序的链**，
而且**每一次拒绝都必然产出一条决策** —— 因为决策行由路由层统一写，
不再由"下单成功"来触发。用户第 3 条要求（决策不止）从此是结构保证，不是补丁。

### 3.3 持仓管理者（接上 `position_guard`）

**这是全案对用户第 4 条提问的直接回答。**

用户问：「这样的话，你人工仓还一定要基于结构失效的判断吗？」

**答案：不需要，而且应该删掉那套判断。** 理由：

- 我上一轮给人工仓的出场判据是三条：熔断 / 观察线拒绝 / 结构失效（`FAMILY_TREND`）。
  前两条站得住（熔断=数学事实；观察线=挂单策略自己的依据）。
  **第三条是我凭空立的**：人工仓没有策略前提，"结构"指的是哪个结构？
  我选了趋势家族，这是个没有依据的默认值。
- 在广播架构里，人工仓和策略仓的差别**只应该有一个**：入场意图的来源不同。
  一旦有了持仓，出场判断就该走同一条勾子链。

具体做法：

```
GuardPosition 由槽位构造（两个槽都转成同一个结构）：
   系统仓：avg_entry=self.pos["entry"], stop_price=self.pos["stop"], liq_price=交易所真值
   人工仓：avg_entry=self.adopted_pos["entry"], stop_price=同上一轮推导的安全止损,
           liq_price=**交易所返回的 liquidationPrice**

每根 K 线：
   read = kline_intent.read_kline(bar15, bar5)        # 每根 K 线都有话说
   for slot in (系统仓, 人工仓):
       if not slot: continue                          # 没有持仓 -> 这些都没有意义
       d = position_guard.decide(slot, price, cfg, kline=read)
       if d.action != HOLD: publish(ExitIntent(slot=..., ...))
```

- `P0`（保命/爆仓缓冲）对人工仓**必须生效**，而且这是唯一"禁止被 K 线否决"的一层。
- `P1`（止损）对人工仓生效 —— 止损价用上一轮已经改成正确口径的那个
  （`爆仓距离/安全倍数`，生产值 1.618%）。
- `P2`（结构离场）**不给人工仓用**。这就是删掉 `FAMILY_TREND` 那个默认值的落点。
  理由：结构离场需要"入场时的结构"，人工仓没有；给它套一个等于编造前提。
- `P3`（分批止盈）/`P4`（加仓）先只给系统仓。人工仓要不要分批止盈是用户的决定，
  不是我能默认的。

**所以对用户问题的正面回答是**：人工仓不基于结构失效；它基于
「保命 + 止损」两条**与策略无关的数学事实**，加上"每一根 K 线都在看"这件事。
`KlineRead` 依然会每根都算（`panic_flush` 会用于 P1 的一次性止损延迟），
但不会成为人工仓的出场理由。

### 3.4 每根 K 线都有话说 —— 落到代码

现在 `_step_pending` 里已经算了 `kline_view`（见上一轮 `_step_pending` 的 `kbar_view`），
但出场判断不读它。改造后：

```
每根 15m 收盘：
   read = read_kline(...)
   db.log_bar_read(read)          # 新增：把"这根K线怎么读的"落库，可回溯
   publish(BarRead(read))
   → 决策者订阅（入场辅助）
   → 持仓管理者订阅（出场辅助）
   → 看板订阅（展示）
```

用户说「K线演化即辅助入场也辅助下游」，这就是它的代码形态：
**一份读数，三个订阅者**，而不是现在"入场算一遍、出场各算各的"。

## 4. 迁移路径（分四步，每步可独立上线、可独立回滚）

| 步骤 | 内容 | 风险 | 可回滚 |
|---|---|---|---|
| **A** | 建 `events.py` + `order_router.py`，**只把现有下单/拦截搬进去**，行为零变化（同一套判据、同一个顺序）。全量测试必须绿。 | 低 | 是（切回直调） |
| **B** | 决策落库改由路由层统一写（取代现在"下单成功才写"）。补齐"拒绝也写决策"。 | 低 | 是 |
| **C** | 接 `position_guard.decide()` 管**系统仓**出场，与现有 `_manage`/`_step_trend` **并行跑一个观察期**（只记录不执行），比对两者结论差异。 | 中 | 是 |

## 5. 这个方案会解决什么 / 不解决什么

**解决**（可验证的）：
1. 决策密度与下单解耦 —— "系统不停，决策不止"变成结构保证。
2. 出场规则从四份实现收敛到一份 —— 上一轮 fee 口径分家那类缺陷不会再出现。
3. 人工仓不再被塞进一个编造的策略前提（`FAMILY_TREND` 那一条删掉）。
4. `position_guard` 的 `check_invariants` 终于进生产 —— 「止损必须在爆仓价内侧」
   这类不变量从"写在文件里"变成"每根 K 线都在检查"。
5. 每根 K 线的读数可回溯（`db.log_bar_read`），出事能查"当时它怎么读的"。

**不解决**（必须说清楚，否则是骗人）：
- **不会让策略更赚钱。** 这是架构改造，不是 alpha。
- **不会自动修好 25% 那个参数**（已单独修）。
- **不会减少一次对账/下单的 HTTP 调用**，可能略微增加（多了 `liquidationPrice` 读取）。
- `position_guard` 的阈值（`target_1_R=2.0`、`safety_multiple=2.5`、`fee_bps=5.0`）
  全是**未经验证的初始值**，接进生产前必须逐个裁决 —— 这会带来新的"策略参数"决策点。

## 6. 风险与代价（说实话的部分）

1. **动 `_step` 是最高风险动作。** 全系统约 4300 行的引擎，`_step` 是唯一入口。
   一个分支顺序写错，后果是"该止损没止损"或"重复平仓"。
2. **并行期双写**：C 步观察期两套逻辑同时算，日志量翻倍，且必须严格保证
   "观察者不产生动作"（否则就是两个引擎同时下单）。这是**最容易出事的地方**。
3. **`position_guard` 从未在生产跑过。** 它在测试里通过，但测试用的是构造的
   `GuardPosition`。真实 `liquidationPrice`、真实资金费率、真实强平规则都可能让它的
   假设不成立。必须有观察期，不能直接信任。
4. **人工仓的 P1 止损依赖止损价正确**。上一轮已修成 `爆仓距离/安全倍数`，
   但那是**按配置推算**的，不是交易所返回的 `liquidationPrice`。方案里要求
   `live.py:157` 的 `position()` 把 `liquidationPrice` 一起返回（现在被丢弃）。
5. **`P2` 结构离场如果将来要给人工仓用**，必须由用户指定"什么结构"，不能我默认。

### BUS-D 顺带修掉的**既存缺陷**（两处，都不是本次引入的）

**1. `_adopted_bars` 在真实行情上恒返回空 —— 接管仓的结构判据从未执行过**

`feed.Bar` 的字段是 `open_time`，而 `_adopted_bars` 用 `getattr(b, "ts", 0)` 过滤，
每根都取到 0，`0 >= anchor` 恒为 False。实测（用真实 `Bar` 跑 400 根、锚点第 300 根）：

```
带 .ts 的假对象 -> 保留 100 根（期望值）
真实 feed.Bar   -> 保留   0 根   ← 恒空
```

后果：`_step_adopted_exit` 每次都在「还没有接管之后的已收盘 15m」就 return。
也就是说，那两条被用户质疑的结构判据**不只是设计可疑，还是从未运行的死代码**。

测试之所以没抓到：夹具 `_bars()` 造的是带 `.ts` 的假对象，真对象没有该字段 ——
这个项目栽过 8 次的同一个错（同一事实两个来源）。
修法：新增 `_bar_ts()` / `_bar_ohlcv()`，按**字段名**逐个试，兼容三种真实存在的
bar 形状；并用**真实 `feed.Bar`** 钉成回归测试。

**2. `maintMargin` 是凭空捏造的字段**

`position()` 一度写了 `p.get("maintMargin", 0)`，注释称"守卫可用于核对维持保证金"。
用只读探针打真实 `/fapi/v2/positionRisk` 后确认：**该字段不存在**。
于是那行永远返回 0 —— 一行装成数据源的假字段，没有任何报错。
已删除，并把实测到的字段清单写进 docstring。

### BUS-D 未做的部分（需要你另外决定）

**系统策略仓（`strategy=pending`）的出场仍由 thesis 状态机执行**，
没有切给 `position_guard`。原因：

* 趋势链的出场是「熔断止损 + 唐奇安破位出场」，剥头皮链是
  「止损/止盈/trail/breakeven/超时」，`pending` 链是 thesis 状态机
  （stop/target/surprise/观察线/结构）。
* `position_guard` 提供的是 P0→P5（保命/止损/结构/分批/加仓/持有），
  **没有止盈目标、没有持有超时、没有唐奇安出场**。
* 一次性"全部移交"等于同时删掉三条策略各自验证过的出场依据，
  远超"接线"的范围。

按你的架构说法（「有了持仓单之后就发出信号，K线演化等出场、止盈、止损等都有了勾子」），
系统仓其实**已经有这些勾子**了 —— 只是实现在 `thesis.py` 而没在 `position_guard.py`。
要不要把它们合并到守卫里，是一个独立的重构决定，等你定。

**2026-11-24 裁决：(a) 保持现状** —— 系统仓继续由各自策略管出场，
守卫只管人工仓。所以上表 BUS-D 的"✅"含义严格是「人工仓这条链通了」，
不是"全系统出场统一"。

## 7.2 A/B/C/D 之后的**全链路审查**（2026-11-24 晚）

用户看到四步都上线后问：还有剩余吗？真实答案是**A/B/C/D 只压掉了
各自那一条链的出口**，四条入口、四条出口里各通了一条：

| 链路 | 走统一出口的路径 | 仍走原路径 | 说明 |
|---|---|---|---|
| 入场 | `_step_pending` → `OrderRouter.route()` | 趋势链 `:1943`、剥头皮链 | 仍直接调 `can_open` |
| 出场 | 人工仓 → `exit_executor.plan_exit()` | `_close`、`_manage`、`_pending_close` | 三条策略各自的出场 |

所以"没有剩余了"这个前提本身要纠正：**改一处闸门不会影响全系统**。
把这一点讲清楚，比宣布完工更有用。

审查（14 项发现，批次 1+2+3 全修）里**最危险的三个**：

### F1 —— 部分平仓会清掉整个槽（BUS-D 自己引入的，最高危）

`_adopted_close` 结尾无条件 `self.adopted_pos = None`。BUS-D 之前它只被
"全量平仓"调用，看不出问题；BUS-D 之后守卫的 `REDUCE` 会带**部分数量**
进来。而库里正躺着一个 25% 止损的遗留接管仓
（`structural_buffer` = 4.15/25 = 0.166），守卫会判
**「减仓 93.4%」**——一次就踩中。

三重后果，全是真金白银：

1. 剩余 6.6% **无人管出场**（没止损、没爆仓保护）；
2. `trades` 里这笔已经"平完了" → **剩余仓在库里不存在**。
   重启后引擎按空仓跑，等 5 分钟对账再重新接管，`entry_ts` 变了，
   "只用接管之后的 K 线"这个锚点历史一起丢；
3. `close_booking` 把**整笔开仓费**摊在这一条部分腿上，pnl 偏负，
   而剩余仓一分成本都不剩。

修法：卖出量 < 持仓量时走部分平仓 —— 内存减仓、**费用按比例分摊**、
`close_trade` 记已卖部分、再补一条剩余 `open` 行让重启接得上；
剩余不足一个步长则**升格为全平**（不留卖不掉的粉尘）。

### F2 —— 人工仓的止损判定每 5 分钟才跑一次（最危险）

唯一调用点在 `_step_pending` 里，而那里先过了
`if ts <= self._pending_5m_ts: return` 这道 5m 节流。
22 倍杠杆、止损 1.618%、爆仓距离 4.05%，5 分钟盲窗相当于
**20~40% 保证金的暴露**——BTC 一分钟就能走 1~2%。

生产跑的正是 `strategy=pending`，所以这不是理论风险。
修法：调用点搬到 `_step`（3 秒粒度、与策略无关、无条件执行），
判据只剩 `if self._is_adopted():`。

### F4 —— `stop == 0` 被读成"止损在 0 元"

唐奇安仓**合法地没有硬止损**（`_fallback_stop` 里 `stop=0`）。守卫看到
`stop_price=0` 会算 `d_stop = 入场价 - 0 = 入场价`，结构性缓冲
≈ `0.04` 倍 → 判**减仓 98.4%**。那不是守卫激进，是我们在用错的语言
问它：它以为这家公司在 0 元设了止损。

观察期若照此记录，报表上会天天出现"守卫要砍 98%"的假分歧，
把真正的分歧淹掉。修法：`stop <= 0` 时观察期直接跳过（并**写明原因**，
不许静默），人工仓则**补一个止损**（爆仓距离/安全倍数）再判。

### 浮点刀锋的最终修法（用户裁决 ②）

选 ②「执行侧要求好手数」，不选加容差或留余量的原因：
容差只让**这个算式**不再产生那个数；而"下发一个小于步长的数量"是
**任何来源**都可能犯的错（仓位取整、部分成交、外部改仓、将来新规则）。
门槛放在唯一出口上，所有来源一次覆盖。

实测确认修复有效（22x 逐仓，止损顶到上限 1.6182%，步长 0.001）：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 守卫结论 | `REDUCE` 平掉 `8.99e-17` | 守卫结论不变（数学正确） |
| 执行层 | 照单全收 → 一张注定失败的指令 | 取整后 < 步长 → `HOLD`，`why_not="too_small"` |


### BUS-C 观察期发现的**真缺陷**（已由 BUS-D 用裁决 ② 修掉）

`position_guard` 的 P0-b 减仓判据存在一个**浮点刀锋**，一旦接线就会每个周期
发出一张"减仓 0.0%"的指令：

| 项 | 值 |
|---|---|
| 爆仓距离 `liq_distance_pct` | `4.045454545454546` % |
| 最大止损 `max_stop_distance_pct` | `1.6181818181818184` % |
| 两者之比 | **恰好 2.5**（= `safety_multiple`） |
| 止损正好顶到上限时 `structural_buffer()` | `2.4999999999999925` |
| `decide()` 的结论 | `REDUCE`，理由「结构性缓冲 2.50 倍 < 2.50 倍，减仓 0.0%」 |
| 要求平掉的数量 | `8.99e-17` BTC |

**根因**：`max_stop_distance_pct = liq_distance_pct / safety_multiple` 让
"止损取到上限"与"缓冲正好等于 `safety_multiple`"成为同一个点，
而 P0-b 的判据是严格小于。于是这个点上浮点表示误差（7.5e-15）就足以翻转结论。

**安全余量实测**：止损取上限的 99.9% → 缓冲 2.5025 → `HOLD`；
生产现有三条预期止损 1.546% → 缓冲 2.617 → `HOLD`。当前无影响，
但这是一颗只在"止损刚好压线"时引爆的雷。

**建议修法（BUS-D 采纳其一）**：
1. 判据加容差：`structural_buffer() < safety_multiple * (1 - 1e-9)`；
2. 或在执行侧要求 `close_qty >= 交易所 step`，不足则视为 `HOLD`；
3. 或把上限留 5% 余量：`max_stop_distance_pct = liq / (safety_multiple * 1.05)`。

**用户裁决：采纳 ②**（「2执行侧要求手数！开工D」）。
已实现在 `trading/exit_executor.py`，详见上文 BUS-D 小节。

**为什么本轮不改**（这一句是当时写的，保留作记录）：BUS-C 的契约是
「只记录不执行、不改交易行为」。在观察期内悄悄改掉被判模块的规则，
会让"守卫与现状差多少"这个基线失去意义。

### BUS-C 的分歧率怎么读（样本待收）

观察需要**有系统仓**才会产生记录（用户原话：「没有持仓这些都没意义」）。
上线时账户空仓，所以 `guard_compare` 目前为 0 行 —— 这是正确行为，不是没接线。
拿到样本后用这两条读：

```sql
-- 分歧条数 / 总观察条数
select count(*) as total,
       sum(case when gate_json like '%"ok": false%' then 1 else 0 end) as diverged
from decisions where action = 'guard_compare';

-- 最近 20 条对照内容
select ts, reason from decisions where action = 'guard_compare'
order by id desc limit 20;
```

判据：分歧率 = `diverged / total`。BUS-D 的启动条件是先把每一类分歧
逐条解释清楚（守卫对/引擎错、引擎对/守卫错、双方都对但时点不同），
而不是一个比例阈值。


### 第 4 条那个问题的答案：人工仓**不需要**结构失效判断

用户问：「这样的话，你人工仓还一定要基于结构失效的判断吗？」

**不需要。** 理由是结构性的，不是口味问题：

- `P2`（结构失效）需要一份**入场时建立的结构**。人工仓没有 ——
  用户为什么在那个价位开、打算拿到哪、能忍多少回撤，系统一概不知道。
- 我之前给人工仓默认套 `FAMILY_TREND`，是**我自己发明的前提**，不是用户给的。
  前提本身就不成立，结论自然也不成立。
- 人工仓正确的判据只有两条**与策略无关的数学事实**：
  `P0` 保命（离爆仓还有多远）+ `P1` 止损（止损 = 爆仓距离 / 安全倍数）。

并且「每根 K 线都有话说」与上面不矛盾：`KlineRead` 仍然每根都算，
但对人工仓**只用于 P1 的一次性 `panic_flush` 延迟**，
永远不作为「所以该出场了」的理由。K 线演化继续辅助入场，
只是不许替人工仓发明出场依据。
