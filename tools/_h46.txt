## 六点四十六、修掉 Guard 峰值不持久化，并连带修掉哨兵日报的自相矛盾

### 一、Guard 的 60% 硬停线每次重启后静默失效

峰值放在内存里，进程一重启就归零，第一次 `update()` 把它设成**当时权益**。
于是第 1 条闸度量的不是「从峰值回撤」，而是「从上次重启回撤」。

实测漏判：真实峰值 190、权益跌到 40（真实回撤 **78.9%**），重启后峰值为 80，
Guard 只看到 50%，60% 硬停**不触发**。部署、服务器重启、OOM 都会重启——不是理论风险。

**修法**：`TradeDB` 加模块级 `strategy_start_ts_at` / `peak_equity_at`，`Guard` 构造时从库恢复。

为什么写成模块级而不是方法：guard 持有 `TradeDB` 对象，sentinel 只持有**库路径**。
同一个「回撤」概念在两处算出两个数，而 **guard 才是真正下闸的那个**。

线上确认恢复路径真的执行了：

```
[GUARD] 已从库恢复峰值 71.7703（策略 trend）
peak_equity(策略时代内) = 71.77029
peak_equity(全历史)     = 104.743808
```

**「按策略切分」这次真的在起作用**：用全历史会永远显示 31.5% 回撤——
正是 sentinel 早先修过的那个假警报。

### 二、顺手撞见同类的第三个实例：哨兵日报自相矛盾

重构完让 sentinel 也用共享实现，然后去看它的日报——生产上真实输出：

```
权益 71.77U，本次运行累计 -28.23U（-28.23%），距峰值回撤 0.0%
当前空仓
巡检无异常。
判断：本次运行已亏损超过 25%，建议立刻停手复盘（可 systemctl stop ai-trader）。
```

同一份报告既说「回撤 0.0% / 巡检无异常」，又建议关掉系统。
那 −28.23% 全部来自**已废弃的剥头皮策略**；趋势策略 0 笔成交、权益没动过。

对一个「不做策略决策」的用户，这条建议会让他关掉一个没出问题的系统。

这和第 41 轮（大屏战绩属于废弃策略）、第 44 轮（Guard 峰值不持久）是同一类病：
**基准属于另一个策略**。

### 三、我自己这轮踩的坑

第一版写成 `ts >= 策略开始` 取之后第一条权益。测试立刻抓出来：报 **0.00**。
因为库里通常没有正好落在策略开始那一刻的记录，取到的是**已经亏过之后**的值，
基准于是变成当前值，累计永远报 0。

正确语义是：策略开局时带着的资本 = 策略开始**之前**最后一条权益。

> 第一次的写法会让「累计」这个数字永久失效，比原缺陷更糟——
> 而且它静默地报 0，看起来像「一切正常」。

### 四、验证

| 变异 | 结果 |
|---|---|
| 去掉 `_restore_peak` | guard 测试失败 → 确实钉住 |
| 基准改回全历史最早一条 | sentinel 测试失败 → 确实钉住 |

修复后的日报：

```
权益 71.77U，本次运行累计 +0.00U（+0.00%），距峰值回撤 0.0%
当前空仓
巡检无异常。
```

239 个测试全绿（新增 8 条）。三服务 active，0 ERROR/CRITICAL，哨兵 OK。

### 五、一个必须说清的判断

这三轮连续修的都是**只在重启/换策略时暴露**的缺陷，它们全都有同一个特征：
**日常验证看不出来**。

> 我不再相信「跑起来没问题」这个结论了。

继续按「基准属于谁、谁写谁读、重启后还在不在」这三问去查。
