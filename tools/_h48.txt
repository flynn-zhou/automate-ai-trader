## 六点四十八、审计实盘下单路径：部分成交会导致永久熔断

### 一、为什么做这件事

趋势策略至今 **0 笔成交**，而实盘下单路径马上要接管真钱。
按方法原则「审计从未执行过的代码路径」，这是当前最大的未知风险。

### 二、缺陷一：部分成交让系统永久停止交易

`market_order` 的余额核对：

```python
before = 持仓
... 下单 ...
after  = 持仓
expected = before + qty        # <- 用的是【请求量】
if abs(after - expected) > 容差:
    回滚 + self.halted = 消息   # <- 永久停摆，只有人工重启才恢复
```

实测三种情况：

| 成交量 | 结果 |
|---|---|
| 100% | `ok=True` |
| 60% | `ok=False`，`halted=余额核对失败：期望 0.00050000，实际 0.00030000` |
| 0% | `ok=False`，`halted=余额核对失败：期望 0.00128000，实际 0.00000000` |

**为什么严重**：

1. 部分成交是市场的**正常事件**，不是错误。
2. 触发后 `self.halted` 被置位，之后**所有**下单都返回「已熔断」，一次正常的部分成交能让系统永久停止交易。
3. 它还会「回滚」：把真买到的那部分卖回去，该建的仓根本没建。

### 三、修的时候发现更深一层：顺序错了

手续费的解析（`fee_base`）原来在余额核对**之后**。

> 也就是说核对时根本还不知道手续费扣在哪个币上——**算法的输入都没有**。
> 这不是算错，是顺序错。

修法：`expected` 用 `filled`（实际成交量）算，买入再减 `fee_base`；成交量为 0 单独处理成干净失败，不熔断。

但**这个检查本身必须保留**——它防的是「回报说成交、余额却没动」。
所以我特意加了第四条测试：余额真的没动时，仍然必须熔断。

### 四、缺陷二：我先猜错了，必须记下来

我看到 `SpotExecutor.halted` 没有告警接入，而熔断文案
`已熔断：余额核对失败：…` 一个关键词都不命中哨兵 4.5 的匹配集合。
于是判断：熔断后系统静默停止交易，和「在等信号」看起来一样。

**第一次写的测试「通过」了——但那是假的。** 因为我手工往 `decisions` 表插了一行 `action='skip'`，
等于把结论先做出来了。

改成跑**真实引擎路径**之后才看清事实：

```
引擎记的是 signal='trend_up', action='skip',
            reason='下单失败：已熔断：余额核对失败：…'
哨兵第一支条件 (signal LIKE 'trend%' AND action='skip') 直接命中。
实测 trend_blocked_2h=1，issues 有内容。
```

**报警是好的。我的假设错了。** 这是第九次。

### 五、但真实的问题还在：大屏看不出来

哨兵每 2 小时吼一次，可用户盯着大屏时看到的仍是「空仓等待 / 涨到 X 就开」。
和上一轮修的 guard 是同一个问题：**状态对了，因果没说出来**。

`engine.state()` 加了 `executor` 字段，大屏把熔断画进因果链。画的时候还修了一个措辞错误：

| 情形 | 修复前 | 修复后 |
|---|---|---|
| guard 拦住 | 安全闸拦截：不会开仓 | 安全闸未放行，即使触发也不开 |
| 执行器熔断 | 安全闸拦截：**原因未提供**（闸明明是放行的） | 执行器已熔断，即使触发也不开 |

### 六、验证

变异检查两条，各自回退后测试变红。**255 个测试通过**（新增 7 条）。
三服务 active，0 ERROR/CRITICAL，哨兵 OK。
真浏览器验证：安全闸渲染正常，页面级 error **0**。线上 `/api/trade/state` 已带 `executor` 字段。

### 七、这轮学到的

> 「先写一个会失败的测试」还不够，
> 测试的**输入**必须来自真实路径，不能是我手工摆出来的场面。
> 我摆一个 `action='skip'` 进去，等于自己给自己出结论。
