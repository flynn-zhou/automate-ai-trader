## 一、这一步到底产出了什么

一句话：**每根 K 线收盘时，把「那一刻每条观察线在哪个价格」算出来并落库。**

它不判断哪条线是支撑，也不产生任何事件/标签。第 3 步的反应层才有「碰到、穿透、收回」，
第 4 步才有事件。这一步只解决一件事：**线的读数要可信、要带来源、要能事后复核。**

    代码      ai_trader/kbar/lines.py    纯计算（EMA / 唐奇安 / 结构位 / 区间四线）
              ai_trader/kbar/store.py    data/kbar.db 的 kbar_line / kbar_meta
              ai_trader/kbar/build.py    只读取数 → 计算 → 落库
    探针      tools/probe_kbar_lines.py  打印真值 + 与看板/策略/生产库逐项比对
    测试      tests/test_kbar_lines.py   25 条（1 条需 KBAR_RANGE_DB 才跑）

## 二、落库位置与表

**新库 `data/kbar.db`。生产在用的 `market.db` / `market_range.db` 只读，绝不写。**

为什么不用那两个库：一次 `CREATE TABLE` 就写了生产库，而写库的时机是「服务正在跑」；
回填要整段重写历史时，事后也分不清动的是行情还是新能力。

### `kbar_line`（每根 K × 每条线一行）

    symbol, interval_ms, ts(开盘 UTC ms),
    line_key        "ema200@15m" / "range_hard_up@1h" —— 下游唯一引用键
    line_kind       不带周期的种类名
    line_period_ms  这条线自己的周期（EMA200@15m 与 @1h 靠它区分）
    line_price      线在那一刻的价格
    bar_close       本根收盘价（算 dist_pct、也便于脱表复核）
    dist_pct        (bar_close - line_price) / line_price * 100
    src_ts          线值来源那根 K 的开盘时间
    line_ready_ms   该值最早可用时刻 = src_ts + line_period_ms

    UNIQUE(symbol, interval_ms, ts, line_key) → 重跑幂等，回填可中断续跑

### `kbar_meta`

    每次计算把口径参数写进去（`line_params:<symbol>:<周期>`），
    外加 `last_build:<symbol>:<周期>` 的覆盖范围。
    口径跟着数据走 —— 只改代码不留痕，以后没人算得清这个数怎么来的。

### 与设计稿的表关系

设计稿 §6 的 `kbar_evolution` / `kbar_reaction` / `kbar_forward` 是**第 2/3/5 步**的产物。

**原稿漏了一张表**：§6 只写三张，但 §12 第 1 步要求「观察线计算与落库」，
§13 第 1 步验收又写着「与**观察线表**里 1h 的值必须完全相等」——
三张表没有一张能装「每条观察线在每根 K 上的价格」。
2026-11-07 用户拍定 A 方案，已在设计稿补入 **§6 表 0 = `kbar_line`**（v3.1），
本实现落的正是这张表。同时删掉了表 2 的 `touch INT` 列（只存碰到的线，恒为 1 是死列）。

为什么不能只靠表 2：

    kbar_reaction 只记「碰到的线」，
    而「差一点碰到」和「离得还很远」是两件事，第 3 步要用 ——
    `dwell_bars`（连续贴着几根）也需要「线存在但没碰到」才能和「线当时还不存在」区分。
    所以必须先把「所有线在每根 K 上的价格」整份存住，之后再从它派生反应层。

## 三、口径（全部是常量，改这里必须改本文）

| 线 | 公式/参数 | 为什么是这个 |
|---|---|---|
| EMA20/50/144/169/200 | α = 2/(N+1)，**种子 = 序列第一根收盘** | 与 `web/live.py::ema_series` 同一条公式，看板与库必须一致 |
| EMA 预热 | 一根 K 之前必须有 **1500** 根才出线（`EMA_WARMUP_BARS`） | 1500 = 币安单次上限 = 看板取数长度；不足不落库，计入跳过清单 |
| 唐奇安上轨 | `max(high[i-150 : i])`，**不含当根** | 与 `trading/donchian.py` §口径 逐字一致；含当根则「突破上轨」永不成立 |
| 唐奇安下轨 | `min(low[i-75 : i])`，不含当根 | 同上 |
| 前高/前低 | `max(high[i-20:i])` / `min(low[i-20:i])`，不含当根 | 参照系必须是「已经发生的价格」，含当根会跟着被测对象一起动 |
| 摆动高/低点 | 严格局部极值（`>`），半窗 k=3，**右侧确认** | 等 j+k 收盘才能确认；提前用就是偷未来 |
| 区间演化 | S=soft_up/soft_dn，R=hard_up/hard_dn，K=v11_key，P=顺向边界 | **只读库不重算**；周期固定 1h |

`dist_pct = (c - p) / p * 100`（设计稿 §7）。距离是口径，不是判断标准。

### P 顺向边界为什么要单独命名

库里没有 `lo_b/hi_b` 两列，P 按方向折叠进了 soft_*：

    DOWN: soft_up=S,  soft_dn=lo_b=P, hard_up=hi_b=R, hard_dn=NULL
    UP  : soft_up=hi_b=P, soft_dn=S,  hard_up=NULL,   hard_dn=lo_b=R

所以 `range_p@1h` 是**还原出来的**（`lines.range_p()`），并与 `range/api.py::_row` 交叉核对过。
不单独命名的话，下游会把 P 当成 S —— 而 v11 纪律明确要求 P 与 K 分开命名。

### 线名规则

    line_key = "<kind>@<period>"      ema20@15m / donchian_hi@15m / range_hard_up@1h

周期后缀用 `3m/15m/1h/4h` 这套写法（`lines.period_label()`）。
**改格式等于改库**，因为它是下游唯一的引用键。

## 四、防偷未来（这一步最容易被做错的地方）

一条线只在「它的来源 K 线收盘」之后才可用：

    line_ready_ms = src_ts + line_period_ms   <=   bar_ts + interval_ms

边界取 `<=`：**恰好同一时刻收盘的线可以用**，那一刻值已经确定，不是未来信息。

### 15m K 线 × 1h 观察线（设计稿 §12 的硬要求）

    15m 的 12:00 那根（覆盖 12:00~12:15，收盘 12:15）
        → 只能用 11:00 那根 1h（覆盖 11:00~12:00，12:00 收盘）
        → 不能用 12:00 那根 1h（13:00 才收盘）= 偷 0.75 小时未来

实现落在 `lines.range_lines_at()` 的二分条件 `ts + 1h <= bar_close`，
并且 `build_bar_lines()` 末尾对整个结果集做一次集中校验，越界直接 `RuntimeError`
（防的是以后有人加新线忘了设 ready）。

### 摆动点也是同一个问题

`high[j] 是 ±3 根内最高`要等 j+3 收盘才成立。所以枢轴 j 记 `src_ts = ts[j]`、
`line_ready_ms = ts[j+3] + interval`，两列一起就能事后回答「当时到底用了什么」。

## 六、已知取舍（都是故意的，不是漏了）

1. **EMA 前 1500 根不出线。** 宁可不出，也不给下游一条没收敛的线；
   跳过清单会写 `ema200:warmup 1499` 这种计数。回填长历史时前面那段确实没有 EMA。
2. **未成形的区间行只有 K 没有四线。** v11 里 K 是「每根 min/max、无滞后、只记录」，
   四线要等成形。这两种情况在跳过清单里分别记 `null_in_db`，能看出是哪一种。
3. **不接 `main.py`。** 第 1 步是「算得对、落得住」，实时逐根推进属于第 2 步之后的事
   （第 2 步要一起决定回填与实时的分界）。
4. **只有与 K 线同周期的均线。** 设计稿第一批就是这么定的（EMA 周期 = K 线周期）。
   「一根 3m 同时遇到多条不同周期线」是验证目标，不是第 1 步的范围；`line_period_ms`
   已经把这条路留好了。

## 十、数据来源与覆盖矩阵（这一步最容易被想当然的地方）

15m 历史不是一处来的，**必须合并三份**，实测覆盖如下：

| 源 | 内容 | 覆盖 | 有量能 |
|---|---|---|---|
| A `market.db bars(900000)` | 真实 15m，带 `b`/`s` | 1,139 根（2026-10-26 11:30 起） | ✅ |
| B `backtest.db klines('1m')` 聚合 | 1m 聚合成 15m，带 `v` 与主动买量 | 11,521 根（2026-07-04 起） | ✅ |
| C `data/range_bars_15m.csv` | 只有 `ts,o,h,l,c` | 17,280 根（2026-05-08 起） | ❌ |

合并优先级 **A > B > C**，合并后 **17,654 根，2026-05-08 04:15 .. 2026-11-07 08:00**，
其中 12,189 根有量能。

### 三个字段同名不同义 —— 踩过就会静默算错

    market.db    b = 买入量   s = 卖出量        实测 b + s == v 精确成立（541/541 根）
    backtest.db  b = 主动买量(base)  s = 主动买**报价额**(quote)
                 例：v=11.895, b=11.264, s=874766.36 —— 若把 s 当卖出量，
                 taker_buy_ratio 立刻变成天文数字

所以 `taker_buy_ratio` 一律用 **b / v**，`load_1m_as_15m()` 干脆**不产出** `sell_vol` 字段，
从接口上杜绝误用。已写成测试 `test_load_1m_ignores_sell_quote_column`。

### 合并冲突不静默选边

三源重叠时逐字段比对（相对容差 1e-9），不符就保留高优先级值**并逐条记入冲突清单**。
实测本次 3 处冲突，全部可解释：

    2026-11-01 02:30  A vs B  c/v 不符  —— B 的 1m 序列在此结束，最后一桶不完整
    2026-07-04 02:30  B vs C  o/h/l 不符 —— B 的首桶只有 7 根 1m
    2026-11-04 04:00  A vs C  c 不符    —— C 的末尾根与生产 15m 的收盘差

> 附带查出的一件事：**本地 `data/market.db` 在 2026-10-31 17:45 那根 15m 是坏的**
> （o/l/v 与生产快照、1m 聚合都不符），生产快照在那根上是一致的。
> 用本地库跑会多出 1 处冲突，用生产快照跑则不冲突。回填请用生产只读快照。

### 内路径只有最近约 7 天

`config.StoreCfg.tick_retention_hours = 168`，`store.py::prune()` 删掉
`interval_ms < 180000` 且超期的行 → 3s/15s/1m 都被裁掉，3m/15m 永久保留。
实测 3s 覆盖窗 2026-10-31 16:15 .. 2026-11-07 08:30，**只有 640 根 15m 落在这个窗内**，
其余 16,944 根的内路径必然为 NULL。

因此本步的覆盖是**分层**的，报数时不许混为一谈：

    结构   17,654 根（全覆盖）
    量能   12,189 根（A+B 段）
    内路径 640 根（3s 窗内），其中 491 根算出 conc ✅
    zone   8,891 根（range_evolution 从 2026-08-04 22:00 起才有行）

## 十一、口径（全部是常量，改这里必须改本文）

设计稿 §7 明确给了公式的，逐条对上；**没给的，不许自己发明**。

| 字段 | 口径 | 常量 |
|---|---|---|
| `body_pct` | `|c-o| / (h-l)` | — |
| `up_wick_pct` | `(h-max(o,c)) / (h-l)` | — |
| `dn_wick_pct` | `(min(o,c)-l) / (h-l)` | — |
| `close_pos` | `(c-l) / (h-l)` | — |
| `dir` | `c>o → 1`，`c<o → -1`，相等 → 0 | — |
| `vol_rel` | `vol / median(前 20 根的 vol)`，**不含当根** | `VOL_REL_N=20` |
| `vol_slot_rel` | `vol / median(同日内槽的历史 vol)`，只用过去 | `SLOTS_PER_DAY=96`, `VOL_SLOT_MIN_SAMPLES=20` |
| `taker_buy_ratio` | `b / v`（主动买量 / 总量） | — |
| `conc` | `max(3s 桶量) / 这根总量` | `TICK_INTERVAL_MS=3000`, `TICKS_PER_BAR=300` |
| `t_low_min` / `t_high_min` | 最低/最高价出现在这根的第几分钟 | 同上 |
| `zone` | 收盘价落在四线切出的哪一层（见下） | `SAME_PRICE_REL=1e-9`（浮点容差，非业务阈值） |

三条补充说明，都是「本来会错、查出来才对」的：

1. **`vol_slot_rel` 按「槽」而非「小时」。** 设计稿 §7 正文写「同小时的历史量」，
   字段名却叫 `vol_slot_rel`。15m 一小时后有 4 个槽，用同槽才真扣掉日内效应，
   所以按字段名实现。**这是一个已知的措辞分歧，若要改口径请先改设计稿。**
2. **`vol_rel` 的窗口里有任何一根没有量，就拒算。** 用残缺窗口算出的中位量系统性偏小、
   比值偏大，看起来像「突然放量」——正好制造假信号。同理，无量根**绝不能**以 0
   进入同槽历史（曾这么错过，`vol_slot_rel` 只算出 6,350 根，本应约 10,269）。
3. **`conc` 的判据是「量自洽」而不是「桶数够不够 300」。** `sum(3s) == K线总量`
   （相对差 ≤1e-6）说明这根的量本来就是这些桶加出来的，分子分母同源，缺几个桶不影响比值。
   实测 640 根里 156 根只有 297~299 个桶却与 K 线量**完全相等**；
   按桶数一刀切会把这 83 根误判成算不出。按量自洽判据：491 根算出、149 根拒算。

### `zone` 是怎么定的（纯排序事实，不含阈值）

四线的**角色**由方向决定，这不是挑数据 —— 数据本身就只有一条：

    DOWN 段  hard_dn 恒为 NULL（实测 1,303 行里 0 条有值），价格序 K < P < S < R
             S = soft_up   R = hard_up   P = soft_dn   K = v11_key
    UP   段  hard_up 恒为 NULL（实测   902 行里 0 条有值），价格序 R < S < P < K
             S = soft_dn   R = hard_dn   P = soft_up   K = v11_key
    PRE      四线全空（实测 60 行全空）→ zone 留空并计 `zone:no_levels`

区间名 = 收盘价落在哪两条线之间，用角色字母命名（如 `P-S`），
跌破全部 `below_<最低>`，涨过全部 `above_<最高>`。

两个必须处理的真实情况：

    同价重合    实测 DOWN 段 186 行 hard_up == soft_up。若不合并，一个点被当成两条线，
                切出零宽度区间，名字会退化成 "P-R" 而 S 其实压在 R 上。
                这里合并成一个节点、标签连写 → "P-SR"。曾因此把 96% 的区间标成 "at_S"。
    段首线没画全 实测 DOWN 104 行、UP 95 行缺 S/R。只在**有值的**线之间命名，
                不假装缺席的线在那儿；状态计 `zone:partial_lines`。

实测落库 22 种标签，分布合理（`P-S` 2,899、`S-P` 1,784、`R-S` 692、`P-SR` 672…）。
`seg_idx` = 该 1h 行在自己的 `(fam, seg)` 段内的序号（从 0 起，由行序列算出，
不依赖库里没有的列）。

## 十六、这一步到底产出了什么

一句话：**每根 K 线**碰到**哪几条线，从哪边来的，穿进去多深，收回来多少，收在线的哪一侧。**

    代码      ai_trader/kbar/reaction.py        纯计算（按上一根取线值 / 穿透 / 收回）
              ai_trader/kbar/store.py           新增 kbar_reaction 表
              ai_trader/kbar/build.py           表 0 + 表 1 → 表 2，并回填 n_touch
    回填      tools/backfill_kbar_lines.py      第 1 步全历史回填（**这一步的前置**）
              tools/backfill_kbar_reactions.py  表 2 回填 + 丢弃清单 + 填充率
    探针      tools/probe_kbar_reactions.py     独立重算核对（不复用 reaction.py）
    测试      tests/test_kbar_reaction.py       54 条（13 个变异体全部被抓）

它**仍然不是判断**：不回答「这条线撑住了没有」。它只回答「碰到了、穿这么深、收回这么多」。
「算不算撑住」是出钱的人后面要定的事。

## 十九、这一步最重要的一件事：反应只能用「上一根 K 线」上的线值

这是写代码**之前**就拦下来的。同周期线（`ema20@15m`、`donchian_hi@15m`、`prior_high@15m`…）
在 t 根的值是由 t 根的**收盘价**算出来的，`line_ready_ms = t的收盘 = t+15m`。
拿这个值去判断「t 根里价格有没有碰到它」，就是用收盘之后才知道的数字
去解释这根 K 线内部的走势 —— 偷未来。

实测这个错法的影响（17,654 根 × 17 条线 = 300,118 个 (根, 线) 对）：

    错法（用同一 ts 那行）           触碰 24,246 次
    正确口径（上一根那一行）          触碰 24,075 次
    判定翻转 3,301 处，其中
      错法多报的「假触碰」 1,736 次   ← 占全部触碰的 7.2%
      错法漏报             1,563 次

落库后的直接证据：表 2 的 **24,075 行里有 14,553 行（61%）**，
「用同一 ts 那行」会取到**不同的线价**。这不是理论问题。

### 规则一：取「上一根那一行」，不是「最近一个就绪值」

第一版写的是「对该根 ts，取该线 `line_ready_ms <= ts` 的最后一个值」（二分）。
交叉核对时发现它会**无限期往前带** —— 一条线消失之后仍能取到消失之前的值：

    2026-08-05 01:00..07:00  区间演化全是 PRE（四线全空，v11_key=None）
    2026-08-05 05:15 的 K 线仍拿 02:00 那条 range_key 判「碰到」
    → 用一条已经消失了 3 小时的线做反应

正确规则：**取「上一根 K 线」那一行；那根没有这条线，就是那根上它不存在。**
依据是表 0 的性质：它对每条**存在的**线在**每根** K 线上都无条件落一行，
所以「缺行」与「不存在」是同一件事。

而「上一根那一行」正好等价于「本根开盘前已就绪」：15m 根 `t-15m` 的收盘时刻
**正好就是** `t` 的开盘时刻，那一行用到的信息与本根开盘时完全一样。
所以两条不变量（防偷未来 / 防往前带）由同一个取法同时满足，且不需要再对 ready 做二分。

改完重算，**表 2 从 24,577 行降到 24,075 行，少掉的 574 行全部是 range 线**：

    range_hard_dn  438 → 162      range_soft_dn  875 → 864
    range_hard_up  397 → 149      range_soft_up  801 → 798
    range_key     512 → 477      range_p        926 → 925

15 条同周期线一行没变 —— 正是「只影响会消失的线」的预期形状。

`assert_no_lookahead()` 把规则写成断言而不是注释 —— 看起来没问题的东西一旦错了完全看不出来。
探针里另一套独立实现（不复用 `reaction.py`）也按同一规则重算，24,075 行逐行相等，
且「库里存的集合 == 独立重算的集合」为 `True`。

## 二十、口径（与设计稿 §7 逐条对上）

| 字段 | 口径 | 说明 |
|---|---|---|
| `touch` | `l <= line_price <= h`，含边界 | 无阈值。容差 `TOUCH_TOL_PCT=0.0` 留着但不启用（D-5） |
| `side` | `o > p → from_above`，否则 `from_below` | 用本根开盘价，不用上一根收盘（D-6） |
| `pen_depth_pct` | from_above: `(p-l)/p`；from_below: `(h-p)/p` | **比例 0~1** |
| `recover_pct` | from_above: `(c-l)/p`；from_below: `(h-c)/p` | **比例 0~1** |
| `close_side` | `c>p → above`，`c<p → below`，`c==p → at` | 平局不硬塞（D-7），实测 5 行 |
| `dist_pct` | `(c-p)/p * 100` | **百分数**（唯一带 ×100 的） |
| `dwell_bars` | 留空 | 「贴着」需要距离阈值 = 判断标准（D-8） |
| `nth_touch` | 键 `(fam, seg, line_key)`，换段从 1 重数 | 段缺失的根留空并计数（D-9） |

三条必须记住的：

1. **`pen_depth_pct` / `recover_pct` 叫 `_pct` 但设计稿公式不带 ×100**，是 0~1 的比例，
   与 `body_pct` 一致；**只有 `dist_pct` 是百分数**。这个不对称会静默坑下游，
   已写成测试钉住（`test_pen_and_recover_are_fractions_not_percent`）。
2. **`recover_pct` 可以大于 `pen_depth_pct`** —— 穿进去又站到线的另一侧时就是这样，
   那正是最值得看的情形，不是错误。实测占 49.09%。
3. **`side` 选错会让穿透/收回整体反号**，而且不报错。所以固定用开盘价。

### `nth_touch` 按段重置（这一条动了设计稿的验收要求）

设计稿 §6 表 2 写「第几次触碰（按区间演化换段重置）」，§13 第 3 步验收要求
「确认 `nth_touch` 在 `(fam, seg)` 变化时确实归零」。原计划是留空（怕自己拍口径），
但那样第 3 步就过不了自己的验收，所以按**字面**实现：

    计数键 = (fam, seg, line_key)   ← 每根 K 线自己带着 (fam, seg)，对全部 17 条线都成立
    换段    counters 从 1 重数
    段缺失  range_evolution 起点（2026-08-04）之前没有段 → 留空，计 nth_touch:no_segment

实测 24,075 行里 **14,664 行有值（60.8%）**，9,411 行 no_segment，
**69 个段的段首值全为 1**。

> 这一条是**本清单里唯一一个「已实现但口径可能不是你想要的」**。
> 若本意是「只有区间四线才按段重置」，改 `_assign_nth_touch` 一处即可。见 D-9。

# 第 4 步 · 事件层（2026-11-07 完成）

## 二十五、先定一件事：表 1 装不下一根 K 线的多个事件

设计稿 §6 的表 1 只有一组 `event / on_line` 列，而 §8.3 要求「事件必须带 `on_line`」。
一根 15m K 线可以同时越过好几条线 —— 实测：

    2026-10-14 12:30  一根同时向下跌破 11 条线
    2026-08-10 02:30  一根同时向上突破 9 条线 + 9 条反包（18 个事件）

若只写表 1，那 11 个事件里会丢掉 10 个。**丢事件就是丢事实**，所以：

| 表 | 装什么 | 行数 |
|---|---|---|
| `kbar_event`（新，表 2.5） | 每个 (根, 线, 事件) 一行，**一个不丢** | 18,873 |
| 表 1 的 `event` 列 | 按 `BAR_EVENT_RULE` 取「穿透最深」的那一个 | 7,328 根有值 |

表 1 只是表 2.5 的一个读法。口径写在 `event_params_snapshot()["bar_event_rule"]` 里，
也写进 `kbar_meta`。这是**实现上的偏离**，登记在待确定清单 D-18 附近。

## 二十六、只用了 14 个词里的 3 个，理由写进代码了

`range_evolution_events` 生产库里的 14 个真实事件名，逐个问了一遍「它能不能落在一条 EMA 上」：

| 词 | 主语 | 能否落在任意一条线 |
|---|---|---|
| `向上突破` / `向下突破` | 线 / 区间边界 | ✅ |
| `突破失败·反包` | 线 / 区间边界 | ✅ |
| `birth` / `区间成形` | 区间自身 | ❌ 线没有「出生」这件事 |
| `上沿确认` / `下沿确认` / `上沿定格` / `下沿定格` | 区间的上下沿 | ❌ 线没有「上下沿」 |
| `反向边界插针上移` / `反向边界插针下移` | 区间的反向边界 R | ❌ 线没有 R |
| `R滚动` | 区间 | ❌ |
| `向上反转` / `向下反转` | 收盘越过区间的反向边界 | ❌ 对一条线来说，越过另一侧**就是突破本身**，再记一个名字会把同一件事记两遍 |

所以 `EVENT_VOCAB_RANGE`（14 个，全量登记）被拆成
`EVENT_VOCAB_USED`（3 个）和 `EVENT_VOCAB_RANGE_ONLY`（11 个），
并且**逐条写了为什么不用**。探针会检查库里没有出现词表外的自由文本（§8.4）。

## 二十七、反包：一个我先做错、靠测试逼出来的语义

第一版把反包判定写在「当根没有穿越」的分支里：

    if ob is not None and ev is None:      # ← 错在这里
        ... 收盘回到原侧 → 反包

结果反包只在**线自己移动到价格另一侧**时才触发（1,043 条）。
「突破后价格穿回原侧」这种最常见的情形，当根本身是一次反向穿越（`向下突破`），
走进了 `ev` 分支，反包分支根本到不了。

发现方式是写测试时发现 `_break_then` 夹具产不出反包 —— 不是靠读代码看出来的。

改成独立判定 + **先记反包、后记当根穿越**：

    for name in (fwd, ev):        # fwd 在前，ev 在后

这样反包那条的 `prev_event` 正好是被反掉的那个突破，
与设计稿 §8.4 的例子 `event=收回, prev_event=向上突破` 形状一致。

代价（如实记录）：反包条数 1,043 → **6,543**，成为数量最多的事件。
原因是一根振荡 K 线现在会同时记「上一个突破失败」和「这次新的反向穿越」两件事。
两种做法都登记在 D-18，等你定。

## 二十八、口径表（已写进 `kbar_meta` 的 `event_params:*`）

| 项 | 值 | 依据 |
|---|---|---|
| 穿越判据 | `prev_close <= p < close` → 向上；`prev_close >= p > close` → 向下 | 无阈值，只看换边 |
| 同日不动 | 不给事件 | 否则每根都是事件，等于没有事件 |

    pen_depth_pct(反包且未触线时)
    state(非 neutral 时)

对应的 `undefined_reason` 也一并写进了 `kbar_meta`，让库自己解释自己。

## 三十五、第 5 步：事后层（表 3 `kbar_forward`）

### 35.1 这一层为什么必须物理隔开

设计稿 §六 的原话：「『之后涨了』是事后信息。混进当下读数，回测就偷未来。」
所以不是靠自觉，是靠结构和测试：

| 隔离维度 | 做法 | 怎么验证 |
|---|---|---|
| 表 | 单独一张 `kbar_forward`，不摊进表 1 宽表 | 表 3 只有 `ret1/ret3/ret5/held`，没有 OHLC |
| 进程 | 单独一个 `tools/backfill_kbar_forward.py` | 第 1~4 步的入口不调 `build_and_persist_forward` |
| 代码 | 单独一个 `forward.py` | `lines/facts/reaction/event` 都不 import 它 |
| 测试 | 扫源码的守卫 | `test_current_judgement_path_never_imports_forward`（认 5 种 import 写法） |

**为什么要「扫源码」这种土办法**：`event.py` 里不小心 `from . import forward` 不会让
任何功能变红、不会报错、不会变慢 —— 只会让回测偷未来。这类错法只能靠静态扫描。

### 35.2 口径（D-12 / D-13 的占位，都不是定论）

    ret_k     = c[t + k*interval] / c[t] - 1        收盘对收盘，不扣费
    horizons  = (1, 3, 5)
    held      = 之后 HELD_BARS(=3) 根的收盘，是否一直守在「事件判定那一侧」
    held 参照价 = kbar_event.line_price（事件判定当时那个线价），固定不变
    held 容差   = 0（正好压在线上不算守住 → 留空）

三条都是**占位**，写在一处常量（`forward.py` 顶部），改一个地方就能重算：

- `RET_FEE = 0.0` —— 要不要扣手续费是 D-12
- `HELD_BARS = 3` —— 「守住」看几根是 D-13
- 参照价用**固定线价**还是「每根用线自己当根的价位」是 D-20

第三条值得多说一句：用固定价问的是「价格有没有回到这条**水平**的另一侧」；
用移动价问的是「价格有没有跌破这条线（线在动）」。两种都是合理问题，
但混着用会把「线在移动」和「价格没守住」算成一个数。所以选一个、写死、记进口径表。

### 35.3 粒度：为什么表 3 是「每根一行」而不是「每根×线一行」

设计稿给的表结构是 `symbol, interval_ms, ts, ret1, ret3, ret5, held` —— 粒度是**根**。

这与表 2.5 不同（表 2.5 是每根×线一条），因为：

- `ret1/ret3/ret5` 跟线**没关系** —— 就是价格之后涨跌了多少，每根一个值
- `held` 跟线**有关系** —— 所以它必须靠表 1 的 `on_line` 才能回答「这条线守住了没有」

代价：一根 K 线同时有多个事件时（实测最多 18 条），`held` 只跟着表 1 那个
`on_line`（BAR_EVENT_RULE 选出来的最深穿透、并列取 line_key 小者）。
**这是有损的**，和表 1 的 `event` 列有损是同一个来源。

为了让这个损失可查，表 3 多写了三列（设计稿没有，但不加就没人能回答
「这个 `held=1` 是哪条线的 1」）：

    held_line       是哪条线
    held_ref_price  以什么价为准
    held_side       above / below

### 35.4 真实数据（2026-11-07 实测）

    表 3 行数                17,654  （每根 K 线一行）
    ret1 有值                17,653  （末尾 1 根后面没 K 线）
    ret3 有值                17,651  （末尾 3 根）
    ret5 有值                17,649  （末尾 5 根）
    held 非空                 7,326  （= 有事件的根 7,328 − 末尾不足 3 根的那 2 根）
      held = 1                3,871  占有事件的根 52.8%
      held = 0                3,455  占 47.2%
      held 空                     2  占 0.03%
    held 拿不到参照价             0

**52.8% / 47.2% 这个接近对半的分法是「没结论」，不是「发现了什么」。** 它说明：
把「之后 3 根收盘有没有回到线另一侧」当成「守住」的判据，对这批数据没有区分度 ——
要么是 HELD_BARS=3 太短，要么是「守住」本来就不该只看收盘（D-13 的一部分）。
这一条要记下来，别被后来的人当成「线有一半的时候被尊重」。

### 35.5 探针独立重算

`tools/probe_kbar_forward.py` 不 import `forward.py` 的任何公式，自己重写一遍：

    0 规模与覆盖（表 3 行数 == 表 1 根数）
    1 独立性红线（扫 5 种 import 写法 + build.py 只定义不调用）
    2 等间隔（相邻 ts 差必须恒为 interval）
    3 ret_k 逐根与独立重算比对 + 「比值中位数必须为 1」查方向
    4 held 逐根与独立重算比对（三态分别比）
    5 held_ref_price == 表 2.5 同 (ts, on_line) 的 line_price
    6 无事件的根 held 必须为空
    7 填充率

第 3 条里的「比值中位数」是专门查**方向整体取反**的：如果实现写成
`c[t]/c[t+k]-1`，每一根的正负都会反过来，而「有值、数量对、不报错」——
逐根比对能抓，但一个概要指标更容易看出「整体反了」。

结果：退出码 0，ret1/ret3/ret5 全部 17,583 / 17,581 / 17,579 根与独立重算一致，
held 全部一致，无事件的 10,285 根 held 全空。

### 35.6 变异测试：20 个变异体，第一次只抓到 15 个

漏掉的 5 个都是**测试不够狠**，不是实现错：

| 漏掉的 | 为什么没抓到 | 补的测试 |
|---|---|---|
| held 只看 k−1 根 | 夹具在第 2 根就跌回来了，看不出少看一根 | `test_held_checks_the_last_of_the_k_bars_too`（让第 k 根才跌回） |
| 无事件的根填 held=0 | 只测了 `build_forward`，没测 build 层怎么挑「有事件的根」 | `test_build_and_persist_forward_ignores_neutral_bars` |
| neutral 被当成有事件 | 同上（这就是 35.7 那个 13,366 的真身） | 同上 |
| 自查断言放过「该有值却空了」 | 只测了「不该有值却给了值」 | `test_assert_no_lookahead_catches_a_mid_table_null` |
| 红线破了（`from . import forward`） | 原正则只认 `from .forward`，不认 `from . import forward` | `test_the_isolation_scan_itself_catches_every_import_form` |

最后一条最值得记：**守卫的守卫**。一个认不全 import 写法的扫描器，
等于一条永远绿的假守卫。

补完之后 **20/20 全被抓到**。

### 35.7 做的时候真实踩到的一个错

第一版把「有事件的根」写成 `event is not None or state is not None`，
想把 neutral 的根也算进来（当时的念头是「state 也是事件层的产物」）。后果：

    有事件的根 = 13,366   ← 7,328 真事件 + 6,090 neutral
    拿不到参照价的根 = 6,090

而 neutral 的根 `event` 是空的、`on_line` 也是空的，**没有线就没有「守住」可言**。
它们被收进来之后既算不出 held，又把「拿不到参照价」这个真·异常指标冲到 6,090 ——
真正的异常会被淹没在噪声里。

改成只收 `event` 非空的根之后：7,328 / 0。这就是 35.6 里 M13 那个变异体的真身。

### 35.8 这一步没做的事

- **没有做任何统计**。52.8% / 47.2% 只是描述，不是「这条线有效/无效」的结论。
  要不要设阈值、阈值多少、用什么分组，都是判断标准，得由出钱的人定。
- **没有接实时**。事后层必须等 K 线走完才算得出来，本身就不该在实时路径上。
- **D-12 / D-13 / D-20 三个口径都还是占位**，代码里写成常量，`kbar_meta` 里写明
  「这是占位」，待确定清单里登记着。

## 三十七、怎么验某一根记得对不对（`tools/show_kbar.py`）

### 37.1 为什么需要这个工具

前面三十五、三十六节证明的都是「全表层面」的事（规模、覆盖、指纹、探针逐行重算）。
但「**某一根**的读数对不对」是另一回事，而且这才是人真正会去查的：

    「11-07 23:45 那根，你为什么说它没事件？它明明跌了 300 点。」
    「这根碰了三条线，凭什么说碰了？」

这种问题拿全表统计回答不了，得把这一根的四张表摊开，再**独立重算**一遍。

### 37.2 为什么不能只打印库里的值

因为那只能证明「库里写着这个数」，证明不了「这个数是对的」。
这个项目反复出现「测试通过但功能没接线」，打印自己写的东西是一回事。

所以 `show_kbar.py` 不 import `reaction.py` / `event.py` / `forward.py` 的任何函数，
它按定义从表 0 + 表 1 重算一遍，然后与库里的值**逐项比对**：

    碰到    l <= p_prev <= h        （p_prev 取上一根那一行）
    从哪侧  o > p ? from_above : from_below
    穿透    from_above: (p-l)/p   from_below: (h-p)/p
    收回    from_above: (c-l)/p   from_below: (h-c)/p
    收盘侧  c > p ? above : (c < p ? below : at)
    事件    前一根收盘在本侧、本根收盘在另一侧 → 向上/向下突破
    ret_k   c[t+k*iv] / c[t] - 1

### 37.3 用法

    python tools/show_kbar.py --at "2026-11-07 23:45"              # 默认按北京时间
    python tools/show_kbar.py --at "2026-11-07 15:45" --tz utc     # 按 UTC
    python tools/show_kbar.py --at "2026-11-07 23:45" --chain 8    # 带前后各 8 根
    python tools/show_kbar.py --at "2026-11-07 23:45" --verify     # 只判对错，退出码 0/1

### 37.4 时区必须显式说，不许猜

同一串「11-07 23:45」在 UTC 和 UTC+8 下是两根不同的 K 线，而两者在库里
**都可能有数据，价格都在合理范围**。悄悄选一个会让整份读数对不上，且完全看不出来。

所以工具默认按**北京时间**（`--tz bj`）解释，因为这边的人说时间默认是本地时间，
但会把两个时区都印出来。`--verify` 只判对错不打印明细，便于脚本化。

### 37.5 时间不在库里时，它会说清三件事

    库里覆盖到哪（UTC + 北京两个都印）
    最近的一根是哪根、差几根
    以及为什么：K 线是等间隔的，给定时分必须是 15 的倍数

这一条是刻意做的。否则「查不到」会被误读成「代码坏了」，而实际上只是
数据还没到那个时间点 —— 这正是三十六节重建前的情况。

### 37.6 它自己也要被测

`tests/test_show_kbar.py`（11 条）守三件事：

- 时区换算（UTC 与北京必须差 8 小时，不是差一分钟）
- 重算真的用**上一根**的线价（本根的线价不许参与「碰到」判定）
- `--verify` 在库里写错一条穿透时必须返回 1 并说出哪里不符（否则它只是一张好看的报表）

第三条最重要：一个永远返回 0 的校验器，比没有校验器更危险。

## 三十八、读数层：把客观值变成一句判断（`ai_trader/kbar/shape.py`，2026-11-08）

### 38.1 为什么加这一层

前五步做完，`show_kbar --at "2026-11-07 23:45"` 能印出：

    dn_wick=0.7675  close_pos=0.7675  vol_rel=7.35  taker_buy=0.388  n_touch=3

这是**客观值**，不是**读数**。用户的原话：

> 你这两个值都不太对，值我没看，但是方式不对！你只是包含客观的值，没有判断

「下影 166 点」这个数，读者还得自己在心里换算：166 点算长吗？7.35 倍量算大吗？
三根针里哪一根是「插针」？这些换算每次都要重做一遍，换个人做出来的结论还不一样。

所以加一层 `shape.py`，把那句换算**显式写下来**，可数、可复核、可争论：

    这一根 = 【恐慌盘】
    同时成立：恐慌盘、插针收回、插针
      · 下影 166.0 点 = 全幅 77%，上影 0.1 点 = 0%，收位 77%
      · 插针(down)：影 166.0 点 >= 40 点，占全幅 77% >= 65%
      · 插针收回：穿透后收回 3 条线 —— donchian_lo@15m(75689.00)、range_p@1h(75670.00)、range_soft_dn@1h(75670.00)
      · 恐慌盘：量 7.35 倍 >= 3.0，主动买 0.388 <= 0.45
      · 稳住：本根自己是针，不参与「插针后稳住」

结论在前，证据在后，每个条件都印出实际值与门槛。

### 38.2 它不违反「不许做第 6 步」

设计稿 §12 结尾禁止的是「第 6 步 判断标准」—— 给线定性（「EMA200 是支撑」），
让它变成决策依据。本层**不给线定性，不产出仓位动作**：

    判断标准  产出动作     -> 该不该买
    读数层    产出描述     -> 这根是不是插针

空仓时本层照样输出。它也不判断哪条线是支撑，只说「这根穿透了哪几条线又收回」。
两者的区别是「能不能被验证」：描述可以拿 OHLC 复核，动作不能。

### 38.3 五个状态词（外加「无」）

枚举，不许自由文本（设计稿 §8.4 明确禁止「主力在诱多」这类解释性文字）：

| 状态（常量） | 判据 | 成立的根数 | 占全量 | 作 label 的根数 | 占全量 |
|---|---|---:|---:|---:|---:|
| `恐慌盘` `STATE_PANIC` | **不要求是针** ∧ 价格被打到一侧 ∧ 量 >= 3.0× ∧ 主动方占优 | 437 | 2.48% | 437 | 2.48% |
| `插针收回` `STATE_PIN_RECOVERED` | 插针 ∧ >=1 条观察线被穿透后收回 | 1,197 | 6.78% | 1,131 | 6.41% |
| `插针` `STATE_PIN` | 影线占全幅 >= 65% ∧ 影线 >= 40 点（**只认长影线形态**，见 39.2） | 2,078 | 11.77% | 861 | 4.88% |
| `插针后稳住` `STATE_STABLE` | 前 3 根有同向针（长影线**或局部极值**）∧ 没破针极值（v3 起还要求**中间每根都没破**，见 §四十）∧ 收盘不弱 ∧ 离针 <= 1 倍针幅 | 3,926 | 22.24% | 3,886 | 22.01% |
| `针后远离` `STATE_NEAR_PIN` | 同上但离针 > 1 倍针幅 | 722 | 4.09% | 706 | 4.00% |
| `无` `STATE_NONE` | 以上都不成立 | — | — | 10,633 | 60.23% |

**label 取优先级最高的那个**（`STATE_ORDER` = 恐慌盘 > 插针收回 > 插针 > 稳住 >
远离 > 无），`states` 保留全部成立的，按同一个顺序排。

两列数不同正是因为多状态：一根长下影可以同时是「插针」「收回」「恐慌盘」，
它只贡献一个 label，但三个状态各自都成立。多状态共 1,273 根（7.21%）。
所以「各自成立」加起来比 label 的合计大 —— 这不是算错。

**`states` 里没有「无」。** 「无」的意思是「一个形态都没成立」，它不是一种形态。
所以那样的根 `states = ()`、落库是空串，只有 `label = 无`。
（早先把它塞进 `states`，导致表 5 存空串而现算给 `['无']`，两边对不上 —— 见 39.5。）

`插针` 分方向：下针 1,062 / 上针 1,016。上下影不可能同时过线 ——
`body% + up% + dn% == 1`，而 `2 × 0.65 > 1`。`pin_side` 先判下针只是为了让
同一根永远得到同一个答案，不是因为真会撞上。

**和 v1 的差别（v2 起这几个数变了）**：恐慌盘 86 → 437，稳住 1,565 → 3,992，
无 13,615 → 10,556，插针收回与插针没动。原因见 §三十九。

**v3 又动了一次（只在稳住/远离/无 这三个数上）**：稳住 3,992 → 3,926，
远离 736 → 722，无 10,556 → 10,633。共 82 根改了 label 或 states，
其中 66 根丢了「稳住」、14 根丢了「远离」。**其余四个词一个没动**
（恐慌盘 437 / 插针收回 1,197 / 插针 2,078），因为 `after_pin` 只长在稳住那条支上。
原因见 §四十。

### 38.4 阈值是扫出来的，不是拍的

**影线门槛：65% + 40 点**

| 档 | 下针 | 上针 | 合计 |
|---|---:|---:|---:|
| 影占 >= 60% 且 >= 40 点 | 1,472 | 1,475 | 16.69% |
| **影占 >= 65% 且 >= 40 点** | **1,062** | **1,016** | **11.77%** |
| 影占 >= 70% 且 >= 40 点 | 749 | 713 | 8.28% |

取 65 这一档的理由与两根锚点直接相关：它把 11-07 23:45（下影 77%）和
11-08 04:45（下影 70%）都收进来，同时把 05:00（下影 10%）和 05:15（下影 25%）
都排除 —— 后两根是「针后又被杀一刀」和「稳住」，不是针。
11.77% 与「插针是少数事件」的常识一致。

**为什么必须两个条件**：光看比例，一根全幅 1.5 点的小 K 线，1 点影线就占 67%；
光看点数，一根 500 点的宽幅 K 线，50 点影线只是噪声。两个都要。

**恐慌盘：3.0 倍量 + 主动买 <= 0.45（下针）**
量 `<3.0` 时那根下影只是慢跌里的正常回抽；`taker_buy > 0.45` 时砸下去是有人接的，
不是恐慌。两个条件一起把 2,078 根插针收窄到 86 根（4.1%）。
**分母是 12,169 不是 17,654** —— 有 `vol_rel` 的根只占 68.93%，早期数据没有 3s 逐笔。
量能缺失时 `is_panic` 返回 False，但证据串写「量能或主动性缺失」，不是「量不够」。
（反向用例：上针的恐慌是主动买占优，口径 `>= 1 - 0.45 = 0.55`。）

**稳住的距离尺：1.0 × 针自己的全幅**
不写死点数。针有大有小：一根 216 点的针之后走出 140 点（0.65 倍）还在针的范围内；
一根 40 点的针之后走出 140 点就是另一段行情了。实测 1,961 个「未破针极值」样本：

    距针/针幅   中位 0.57   p75 0.90   p90 1.42   p99 2.85   最大 8.53

取 1.0 倍 → 稳住 1,565 / 远离 396。换成固定点数的代价（探针第 5 段实测）：

| 上限 | 稳住根数 | 与 1.0×针幅 的差 |
|---|---:|---:|
| 1.0 × 针幅（实际用的） | 1,565 | — |
| 固定 50 点 | 639 | -926 |
| 固定 100 点 | 1,120 | -445 |
| 固定 200 点 | 1,592 | +27 |

固定点数会随行情波动整体偏移（波动放大时同一档点数收得过紧，缩小时过松），
针幅尺与行情无关。

### 38.5 一个死条件：`close_pos >= 0.65` 被删掉了

第一版写了三个条件，第三个是「收盘收在全幅上部」。它恒真：

    c >= min(o, c)  ⇒  c - l >= min(o, c) - l  ⇒  收位 >= 下影占幅

所以只要「下影占幅 >= 0.65」成立，「收位 >= 0.65」必然成立。上针同理
（`1 - 收位 >= 上影占幅`）。实测 17,654 根反例 **0 根**，开关这个条件命中数一个不差
（1,472 / 1,062 / 749 完全相同，探针第 3 段前后比对）。

而且「收在最低点的长下影」这种东西根本不存在：`c == l` 时 `min(o,c) - l == 0`，
下影为 0。

这是本项目老毛病「条件写了但没接线」的变体 —— 条件写了，但它永远为真。
留着只会让后来的人以为「这里有个额外约束」。删掉，并把这段推导写成测试
（`test_close_pos_condition_is_mathematically_redundant`），防止有人再加回来。

### 38.6 `SCENARIO_TOL_PTS = 20` 只在一个地方生效

用户原话：

> 容差设置 20，我设置的这个容差只在这一个场景生效！别扩散！

它**只**用在 `after_pin` 的第 3 个条件：「有没有实质破掉针的极值」
（`l >= pin.l - 20`，上针则 `h <= pin.h + 20`）。三个判据
（`pin_side` / `recovered_lines` / `is_panic`）都不带容差。

**绝不许扩散到 `reaction.TOUCH_TOL_PCT`**（那是表 2 的入表条件，现在是 0.0）。
一改 0 → 20：表 2 的触碰行数 24,075 → 30,874，`nth_touch`、表 1 的 `n_touch`、
表 3 的 `held` 全部跟着变。这是两个完全不同的东西，只是名字里都有「容差」。

单位不同，写死在代码注释里：

    WICK_PCT_MIN      无量纲（影线 / 全幅）
    WICK_PTS_MIN      绝对价差，点（BTC 上 1 点 = 1 USDT）
    SCENARIO_TOL_PTS  绝对价差，点
    其余              比值（vol_rel / taker_buy_ratio / 倍针幅）

有两条测试钉这个隔离：`test_the_scenario_tolerance_does_not_touch_reaction_touch_tol`
（两个常量不许相等）和 `test_scenario_tolerance_is_wired_to_tol_pts_only`
（扫源码，容差只许出现在常量定义与 `tol_pts` 默认参数里，跳过 docstring 与注释）。
探针第 4 段实测：容差 20 → 0，针后 1,961 → 1,815，插针/收回/恐慌三个数不动。

### 38.9 不落库

判定**现算、不落库**。理由：

1. 阈值还是临时的（见 D-21）。落库会把「临时阈值」固化成历史数据，
   以后调参就得重建全表，而且已落库的旧判定与新判定混在一起分不清。
2. 判定完全由表 0 + 表 1 决定，重算一遍的代价是读 4 根 K 线 + 1 张线快照，
   没有性能问题。
3. 落库了就要维护「表 1 改了判定要不要跟着改」的一致性，而它现在没有这个问题。

代价是 `--verify` 校验不了判定（库里没有「库里的判定」可比）。
这个代价写进了 `show_kbar` 的 docstring：判定的正确性由
`tests/test_kbar_shape.py`（59 条）和 `tools/probe_kbar_shape.py` 负责。

### 38.10 不 import `forward`

第 5 步是事后层，读的是「之后涨没涨」。「之后涨了」是事后信息，混进当下读数，
回测就偷未来。`shape.py` 只用 `[ts - look*iv, ts]` 这一段，线快照用**上一根**的。

`test_shape_does_not_import_forward` 扫源码钉这条：先滤掉注释，
再把所有 `import` / `from` 语句捞出来，逐条断言不含 `forward`。
（第一版这条测试被自己的 docstring 绊倒了 —— docstring 里写着「不 import forward」，
字符串匹配直接命中。所以扫描必须先滤注释/docstring。）

### 38.11 探针：独立重算

`tools/probe_kbar_shape.py` 不 import `shape.py` 的任何判定函数，阈值也**单独写一遍**
（故意重复 —— 共用常量就失去交叉校验的意义）。七个段落：

    0  规模与覆盖（分母是什么，命中率才有意义）
    1  两根锚点（用户给的验收标准）
    2  四个判据逐根比对 17,654 根
    3  「收位条件是死条件」的独立验证
    4  容差只影响「稳住」
    5  距针尺用固定点数会错判多少根
    6  互斥：同一根不许既是针又是稳住
    7  抽样把证据串印出来给人看（机器只能证明一致，证明不了读得对）

当前结果：`17654 根全部一致（四项判据 + 死条件 + 容差隔离 + 互斥）`。

**写这个探针时踩了两个坑，都记在文件头里：**

1. **收回只对「本根是针」的根有意义。** 一开始拿全部根去比「探针有没有收回 /
   shape 有没有标收回」，5,706 根全报不一致。其实是探针的对比范围错了：
   非针的根就算穿回了一条线，也不该被标成「插针收回」。
   收窄到「本根是针」的 2,078 根 → 不一致 0 根。
2. **回看窗口的 `range` 终点是排他的。** `range(i-1, max(-1, i-look), -1)`
   在 `look=3` 时只给 2 个候选（漏了第 3 根）。这个 off-by-one 让「针后」
   少算 526 根，而且不报错。正确终点是 `i-look-1`。

### 39.2 漏洞一：恐慌盘以「本根是插针」为前提，等于排除了它最典型的形态

v1 的写法是：

```python
if side is not None:                 # 先要求本根是针
    ...
    if is_panic(g, vol_rel, tbr, side=side):
        states.append(STATE_PANIC)
```

而 `pin_side` 算下影用的是 `dn = min(o, c) - l`。**当 `close_pos = 0`（收在全幅最低）
时 `min(o, c) == l`，于是 `dn == 0`** —— 收在最低点的 K 线在数学上不可能有下影线，
所以它永远不是针，也就永远不可能是恐慌盘。

这不是边角情况。按 v1 的恐慌盘量能条件去筛「收位 <= 25% ∧ 量 >= 3.0 ∧
主动买 <= 0.45」的根，全库有 **181 根**，而其中**能被判成下针的只有 0 根** ——
因为收在 25% 以内的根，下影天生就短，`dn_pct >= 65%` 几乎不可能满足。
也就是说 v1 的恐慌盘判据在它最该起作用的形态上，命中率是 0。
10:45 就是这 181 根之一。

（作为对照：`close_pos <= 25%` 或 `>= 75%` 的根全库有 9,650 根，
所以「收在极值」本身不稀罕，稀罕的是**同时**有量、有主动性。）

**修法**：把「方向」与「形态」拆成两件事。

    有没有影线       -> pin_side     （价格的形态）
    价格被按到哪侧   -> panic_side   （价格的位置）

`panic_side` 的口径是**影线优先、收位兜底**：

1. `pin_side(g)` 有结果就用它 —— 价格探出去的方向才是被打的方向；
2. 没有影线才看收位 —— 收在极值 = 价格被按住没回来。

为什么不能只看收位：2026-11-07 23:45 收位 77%（打完被买回来了），
只看收位会判成「上冲」，而它其实是下压后收回（下影 166 点 = 77%）。
为什么不能只看影线：10:45 没有影线，只看影线判不出方向。
两个都要，所以定了优先顺序，并且把它写成 `panic_side` 一个函数 ——
写在 `judge` 里当 if 分支，下一次改判据又会漂。

### 39.3 漏洞二：「针」只认单根长影线，多根跌出来的低点它看不见

11:00 打出这一波最低 75,690.2，但它的下影只占全幅 36%（< 65%），
所以按 v1 它**不是针**。于是 11:15 的「收回 + 稳住」没有参照对象，判成「无」。

而「价格在这里被打住、然后收回」正是用户要看的东西。

**修法**：把「针」扩成两种形态。

| 形态 | 认定条件 | 针幅（当尺用） |
|---|---|---|
| `wick` 长影线 | 影线占全幅 >= 65% 且 >= 40 点 | 那根自己的全幅 |
| `swing` 局部极值 | 往回 8 根里它是极值，且冲进去的落差 >= 40 点 | 那根自己的全幅（下限 40 点） |

`swing` 的**确认范围严格限制在「到今天为止」**：

    j 是 [j-8, end] 里最低的那一根，且低于它前一根，
    且从窗口最高点跌进这个低点的落差 >= 40 点

`end` 是正在判定的那一根。**绝不许写成「后面几根没破」** ——
那是偷未来：第 j 根收盘时不可能知道后面破没破，回测会拿这个赚钱。
探针里有一条变异测试专门验证这一条（把 `end+1` 换成 `len(bars)` 必须红）。

确认窗口取 8 根。**必须说清：这条曲线上没有拐点，8 是权衡，不是数据指着它。**

| swing 确认窗口 | 稳住（各自成立） | 稳住占全量 | 「无」的根 | swing 参照次数 |
|---:|---:|---:|---:|---:|
| 3 根 | 5,257 | 29.8% | 6,702 | 4,595 |
| 5 根 | 4,605 | 26.1% | 7,719 | 3,777 |
| **8 根** | **3,926** | **22.2%** | **8,780** | **2,936** |
| 12 根 | 3,434 | 19.5% | 9,535 | 2,356 |
| 16 根 | 3,111 | 17.6% | 10,092 | 1,952 |
| 24 根 | 2,736 | 15.5% | 10,686 | 1,513 |

（这张表是**跑真正的 `S.judge`** 测的，只换 `SWING_LOOKBACK_BARS` 与各函数的
默认参数；8 根那一行与库里 3,926 / 722 / 8,780 完全对上，说明测的就是现行口径。）

单调下降，没有 elbow。取 8 的两个理由都是判断而不是证据：

- 3 根窗口下「稳住」占 30.1%，一根一个低点，那样「局部极值」几乎等于「任意一根」；
- 24 根窗口下 swing 参照只剩 1,510 次，11:15 那类「跌一段、停住、收回」容易被漏掉
  （11:00 在 [10:45, 11:15] 里是最低，在 24 根窗口里也是 —— 这一根不会漏，
  但更早的低点会）。

所以这个数已经挂进 D-21 等用户定。**不要把它当成「扫出来的最优值」** ——
v1 的 0.65 / 40 点至少有一条「收进来 2 根锚点、排除 2 根」的硬理由，这条没有。

### 39.4 极值针为什么不当 `插针` 标签

`swing` 只当「稳住/远离」的**参照针**，本根不打 `插针` 标签。这是刻意的，
实测理由：若把「本根自己是极值」也算插针，全库 **5,852 根（33.1%）都是插针** ——
下跌趋势里每根新低都满足。那已经不是形态，是趋势的同义词。

所以落库时两个槽位分开：

    side / pin_kind        本根自己是针时的方向和形态（不是针则空）
    pin_ts / ref_pin_kind  「稳住」「远离」时参照的那根针是哪根、什么形态

混成一个字段就说不清「这根的形态是 swing」到底是它自己是极值、
还是它稳住的是个极值 —— 落库后没人能分辨，也没法复核。

现状（v3 落库值）：本根是针 2,078 根（全部是 `wick`），参照针 4,648 根
（`wick` 1,712 + `swing` 2,936）。那 2,936 次 swing 参照来自 **1,958 个不同的根** ——
它们就是 v1 完全看不见的那批（v1 只有长影线一种针）。

### 39.5 针幅用「极值那根自己的全幅」，不用窗口最宽根

「稳住」和「远离」的边界是「离针 <= 1 倍针幅」，所以针幅就是那把尺。
对 `swing` 针没有「自己的影线」可言，试过三种：

| 当尺的东西 | 稳住（各自成立） | 远离 | 结论 |
|---|---:|---:|---|
| **极值那根自己的全幅（下限 40 点）** | **3,926** | **722** | **采用** |
| 窗口内最宽那根的全幅 | 4,154 | 494 | 尺被撑大，远离少 228 根 |
| 冲进极值的落差 | — | — | 11:00 那根算出 1,618 点，177.8 点只占 0.11 倍，几乎全判「稳住」 |

落差只当**门槛**用（`swing_pin_kind` 的 `min_depth`），不当尺 ——
门槛回答「这算不算被打出去」，尺回答「走出去多远算远离」，两件事。
下限 40 点是防极值那根是十字星（全幅 2 点）时除出天文数字。

### 39.6 跨根收回：功能留着，默认关

一开始顺手做了「跨根收回」：针在 `j` 根穿透某条线没收回，`i` 根收回来。
写完后实测（v2 口径，全库 17,654 根，走的是 `build.py` 的真实调用方式）：

| 口径 | 关（现行） | 开 | 变化 |
|---|---:|---:|---:|
| `插针收回` **状态成立** | 1,197 | 5,150 | **+3,953（22.4%）** |
| label = `插针收回` | 1,131 | 4,970 | +3,839 |
| label = `插针后稳住` | 3,886 | 2,559 | **−1,327** |
| label = `针后远离` | 706 | 192 | **−514** |
| label = `插针` | 861 | 716 | −145 |
| label = `无` | 10,633 | 8,780 | −1,853 |

注意「状态成立」与「label」两行不是一回事：`插针后稳住` 这个**状态**在打开后
照样成立（3,926 → 3,926），被抢掉的是 **label**，因为 label 取优先级最高的那个，
而 `插针收回` 排在它前面。混淆这两列会让人以为「稳住不成立了」—— 它成立，
只是不再是这根 K 线的结论。

22.4% 不是少数事件。观察线很密（表 0 里有 17 条不同的线，平均每根 12.96 条），
相邻两根里总有一根收在线的另一侧，所以这个定义测到的不是「针被收回」，
而是「线太密」。开着它还会抢掉更具体的标签：**11-04 11:15 就从「插针后稳住」
变成「插针收回」**。

（v1 时代这套代码量到 6,555 根 / 37%，因为那时还没有局部极值针，
同一口径下 v2 是 3,953 / 22.4%。结论没变、数字变了 —— 两个都记下来，
免得下次看到「37%」以为是另一个 bug。）

处理：`judge(..., allow_cross_bar=False)` 默认关，函数留着（`recovered_after_pin`），
理由和数据写在这里，等以后重新定义。见 D-21。

## 四十 · v3 修正 + 表 6 `kbar_verify`（佐证层）2026-11-08

回头验当时的判断」（§40.2~40.6）。N 由我定，选了 **1 根（主）+ 3 根（看延续性）**。

### 40.1 `after_pin` 只看了「这一根」，中间那几根没人管

`after_pin_full` 原来的判据是「本根没破针的极值」：

    holds = g.l >= gp.l - tol_pts          # down 针，tol_pts = 20

**只比本根一根。** 于是出现这样的情形：

    针在 t-3 根：低点 75,690
    t-2 根：最低砸到 75,600（破了针低 90 点）  ← 没人看
    t-1 根：回到 75,800
    t  根：最低 75,750，收阳                  ← 判「插针后稳住」

事后看这根根本不该叫「稳住」——中间那根早就把针破了。这是**证据链断在中间**，
不是阈值松。

修法（`shape.py::pin_extreme_kept`）：判 `holds` 之前，把 `(j, i]` 每一根都过一遍，
任何一根破穿针极值超过 20 点就不算稳住。

    def pin_extreme_kept(bars, j, i, side, tol_pts):
        """j 的极值到 i 为止，中间有没有任何一根破穿（超过 tol_pts）。"""

**这个 20 点是用户给的、只属于这一个场景的容差**，不许扩散到别处
（见 §40.4 与 D-21）。

实测影响（全库 17,654 根，`--rebuild` 前后对比）：

| 指标 | 修前 v2 | 修后 v3 | 变化 |
|---|---:|---:|---:|
| 稳住（各自成立） | 3,992 | 3,926 | −66 |
| 远离（各自成立） | 736 | 722 | −14 |
| 「无」的根 | 10,556 | 10,633 | +77 |
| 改了 label 或 states 的根 | — | 82 | — |
| 有参照针的行 | 4,728 | 4,648 | −80 |
| 恐慌盘 / 插针收回 / 插针 | 437 / 1,197 / 2,078 | 同左 | **0** |

**为什么另外四个词一根没动**：`after_pin` 只长在「稳住/远离」这条支上，
恐慌盘、插针、插针收回都在它之前判完。这也是一条自检 ——
如果哪天改了 `after_pin` 而恐慌盘数变了，说明改动渗到了不该去的地方。

**「稳住」里参照针不是段内极值的比例**：503 根（12.6%）→ **424 根（10.8%）**。
其中真正超出 20 点容差的：89 根（2.2%）→ **8 根（0.2%）**。
剩下的 424 根全部落在用户故意给的 20 点余量内 —— 那不是 Bug，是容差。

**8 个锚点一个没变**（10:00/10:15/10:30 无、10:45 恐慌盘、11:15 插针后稳住、
11:30 无、23:45 恐慌盘+插针收回+插针、05:15 插针后稳住）。修 Bug 不该动到
本来就对的判断，这条也是自检。

#### 40.1.1 一个差点误判的坑：别重新推方向

第一版探针报了「8 根稳住仍然破穿 >20 点」，看着像修漏了。逐根查下去是**探针自己错了**：
它用 `pin_side(gp)` 重新推参照针方向，而 `judge` 里用的是
`swing_pin_kind(bars, j, i-1)`。8 根里有几根是 swing 针，`pin_side` 给 None
或给错方向，于是拿错了极值去比。

结论：**佐证层必须用表 5 落库的 `ref_pin_side`，绝不许自己重推。**
这就是表 5 为什么要加这一列 —— 方向是判定时的结论，事后重推等于换了个问题。

### 40.2 佐证层（`ai_trader/kbar/verify.py` + 表 6 `kbar_verify`）

**红线（与 `forward` / 表 3 同一条，方向相反）**：

    shape.py 读表 6  ⇒ 判定偷看未来 ⇒ 1.7 万根历史结论全部作废
    verify.py 读表 5  ⇒ 合法（它就是来验判断的）

单向：**表 5 是输入，表 6 是旁注，永不回写。**
`check_kbar_pipeline.py` §7.7 有一条源码扫描检查 `shape.py` 里没有
`import verify` / `kbar_verify`。

**「没有可被推翻的预言，就没有结论。」** 这是这一层的设计原则：宁可写
`无预言`，也不许把一句模糊的话当成了预言再去验它。

预言规则（`PRED_RULES_VERSION = "v1"`，`VERIFY_TOL_PTS = 0.0`）：

| 结论 | 当时的预言 | 参照点 |
|---|---|---|
| `插针`(下影) | 后面不会跌破本根低点 | 本根 `l` |
| `插针`(上影) | 后面不会突破本根高点 | 本根 `h` |
| `恐慌盘` **有影线** | 后面不会跌破/突破本根极值 | 本根极值 |
| `恐慌盘` **无影线** | 后面**会继续**破本根极值 | 本根极值 |
| `插针后稳住` / `针后远离` | 后面不会跌破/突破**参照针**极值 | 表 5 的 `ref_pin_ts` |
| `无` | 后面不会走出 >= 1 倍本根全幅的单边 | 无固定价位 |

两个要说清的地方：

1. **恐慌盘分两支、方向相反。** 有下影（被买回）=「见底」，无影线（收在极值）
   =「卖压没释放完」。同一个词装两件事，见 §40.5。
2. **`插针收回` 只验了「针」那半句。** 它 100% 同时是「插针」，走到插针分支；
   「哪条线收回来了」那半句本层验不了（实测「后面不反向穿线」只有 21.8%，
   比基准 48.6% 低 26.8 点 —— 因为价格本来就天天穿线）。
   **所以预言原文末尾明写「本层只验极值这一半」**，不写就是让人以为半句也验过了。

裁决（四值，不许别的）：

| 裁决 | 含义 |
|---|---|
| `佐证成立` | 后面 N 根确实如预言那样 |
| `被推翻` | 后面 N 根不是那样 |
| `无法判定` | 表尾凑不满 N 根 —— **没验，不是成立** |
| `无预言` | 这句话没有被验的资格（本层实测为 0 行） |

`容差 0 点 = 正好打到就算破`，与本项目 reaction 层 `TOUCH_TOL_PCT=0.0`
「正好等于线价算触碰」同一个口径。用严格 `<` 会把「打到没超过」算成守住，
等于对被验的那个判断网开一面。

### 40.4 命中率必须和同口径基准并排（这是本层最重要的一条）

**「命中 73%」不是结论。** N=1 时「随便一根，本根低点后面不被破」本来就有 53.1%。

### 40.5 三个从数据里翻出来的真问题

#### 40.5.1 恐慌盘一个词装了两个相反的行情

| 恐慌盘 | n | 后面真破极值（N=1 / N=3） | 基准 | 提升 |
|---|---:|---|---:|---:|
| 下压·**无影线** | 180 | 77.2% / 86.7% | 46.9% / 65.0% | **+30.4 / +21.6** |
| 下压·**有下影** | 46 | 15.2% / 30.4% | 46.9% / 65.0% | **−31.7 / −34.6** |
| 上冲·**无影线** | 171 | 76.0% / 85.4% | 46.1% / 64.7% | **+29.9 / +20.7** |
| 上冲·**有上影** | 40 | 5.0% / 17.5% | 46.1% / 64.7% | **−41.1 / −47.2** |

同一句话，有无影线后面走的方向**相反**，两边都是 z>4。
而且那 46 根有下影的**全部同时是「插针」**（label 优先级把插针收回/插针排在
恐慌盘之后？不，恐慌盘优先 —— 是「有下影」这个形态本身让它们同时满足插针），
所以只看 label 永远看不见这半批。

**没有改判定。** 拆不拆「恐慌盘」是口径决定，要用户定，已挂 D-22。

#### 40.5.2 「稳住」在向下方向有信息，在向上方向是反的

按「离参照针多远」分层（**必须在同一桶内比**，否则测的是距离不是判断）：

    N=1  参照针=下针                          N=1  参照针=上针
    桶          稳住    同桶对照   提升        桶          稳住    同桶对照   提升
    0~0.25    79.3%    49.9%   +29.4        0~0.25    55.9%    75.9%   −19.9
    0.25~0.5  89.2%    72.2%   +17.0        0.25~0.5  71.0%    86.4%   −15.4
    0.5~0.75  94.3%    86.0%    +8.3        0.5~0.75  85.9%    91.0%    −5.0
    0.75~1.0  96.3%    92.1%    +4.2        0.75~1.0  93.8%    95.4%    −1.6

N=3 同一个形状（下针 +27.9/+21.1/+12.5/+11.5，上针 −22.5/−17.3/−9.7/−8.8）。

**下针每一个桶都是正提升，上针每一个桶都是负提升。**
含义：价格在下针上方收强 = 有人在守这个低点；价格在上针下方收强 =
买方在顶这个高点，**突破概率更高**。

也就是说「稳住」这个词对上针是**误导**：它标的是「要往上破」，不是「稳住了」。

**没有改判定**（改词或拆状态是口径决定，要用户定），已挂 D-22。
但要提醒：读到 `插针后稳住` 且参照针是**上针**时，历史数据说后面更容易破高。

#### 40.5.3 「针后远离」的提升是距离带来的，不是判断带来的

按距离分层（>1.0 桶里全是远离，没有同桶对照，所以用「去比同桶的稳住」的办法）：

「远离」的 99.2% 看着惊人，但它离针已经 >1 倍针幅 —— 本来就远，当然不容易回去。
把「离针多远」按住之后，提升从 +19.6 塌到 **+3.6**。
这不是说「远离」错，是说**它的高命中率主要来自距离这个混杂变量**，
不能当作「判得准」的证据。

### 40.9 已知取舍（v3 新增）

- **N=1 与 N=3 都留着，不合并成一个数。** N 越大越容易「被推翻」是结构性的
  （时间窗口长），所以两个 N 的命中率不许互相比较，必须各自对各自的基准。
- **容差 0 是刻意的。** 20 点是用户给 `after_pin` 的，不许拿来给佐证层放水 ——
  放水就等于让被验的判断自己判卷。已实测 0/5/20 三档不改变任何结论
  （插针 N3 50.4/51.6/56.7；恐慌盘无影线 N3 86.7/85.6/80.6）。
- **`无法判定` 只有 1~3 行**（表尾），说明没出现大面积缺数据。
- **`无预言` 实测 0 行**：每个结论词都翻出了可被推翻的话。如果哪天涨起来，
  说明有结论词的话变得「不可推翻」了，那要当问题查。
- **`插针收回` 的「线收回」那半句本层没验**，只验了针那半句。

### 41.1 定论：最少 1 根，最多是长尾，p99 = 11 根

原 `VERIFY_HORIZONS = (1, 3)` 是我拍的。实测 `tools/probe_kbar_horizon.py`
（17,654 根，N 扫到 12）后：

| 定型于 | 根数 | 占比 | 累计 |
|---|---:|---:|---:|
| **1 根** | 8,027 | 45.5% | 45.5% |
| 2 根 | 3,278 | 18.6% | 64.0% |
| 3 根 | 1,933 | 10.9% | 75.0% |
| 6 根 | 628 | 3.6% | 90.2% |
| 12 根 | 173 | 1.0% | 100% |

中位 2 根，p90 6 根，p99 11 根。

**N=3 只覆盖 75%** —— 也就是说只报 N=1/3 的时候，四分之一的判断还只是临时答案。
这不是「再加个 N=5」能解决的：曲线是长尾（测到 12 还在以 1.0%/档 下降），
所以正确做法不是选更大的 N，而是**换成「活了多久」这个维度**。

### 41.2 结构性偏差：两类预言的短期裁决方向相反

| 类型 | 短 N 下偏向 | 原因 |
|---|---|---|
| 守住型 `must_hold=True` | **偏松**（容易成立） | 还没来得及破就算成立 |
| 会破型 `must_hold=False` | **偏严**（容易推翻） | 还没来得及破就算推翻 |

实测印证：恐慌盘（会破型）N=1→N=3 命中率 79.6%→84.2%（**上升**）；
插针收回（守住型）76.9%→52.3%（**下降**）。

**所以「label × 同一 N 的命中率」横着比是错的** —— 一半预言在反向计分。
存活层就是为了消掉这个混淆。

### 41.3 新增表 6b `kbar_verify_survival`

一根一个答案（`UNIQUE(symbol, interval_ms, ts)`），三态：

```
已破     第 break_n 根被打脸/被证实 → 定型
活到最后  满 max_n 根都没破 → 看完了
未成熟   后面的根不够 max_n → 还没看完（表尾）
```

⚠ **`未成熟` 与 `活到最后` 的 `break_n` 都是 NULL。** 只按 NULL 统计，会把表尾
「还没验」算成「验完了没破」，命中率凭空变好。`status` 列专门防这个，
`survival_counts()` 只把「已破 + 活到最后」算 `settled`。

`survival_hash = b6da1717a9cc`，**故意与 `verify_hash` 分开** ——
把 `max_n` 并进 `verify_params()` 会改掉表 6 的指纹、全库立刻「过期」，§7.7 会红。
变异测试专门钉了这一条。

实测（17,654 根）：`已破` 14,511（82.2%）、`活到最后` 3,136（17.8%）、`未成熟` 7。
`未成熟` 只有 7 根而不是 12 —— 因为表尾 12 根里「提前破了」的那些**已经定型**
（破了就是破了，不用等满窗口），这是设计对的地方。

按类型分：守住型 n=17,296 破了 82.0%（中位第 2 根，p90 第 7 根）；
会破型 n=351 破了 92.3%（中位第 1 根，p90 第 2 根）。
⚠ 这两个百分比**不许单独当结论** —— 必须配同口径基准（见 §四十.9 的表）。

### 41.4 实时跟随：原来是全量重写，现在有增量

用户问「做到了吗」，实情是**没做到**：`build_and_persist_verify` 每次
`delete_verify(symbol, interval, horizon)` 全删再全插，没有任何增量路径。

新增 `build.update_verify_tail()`：

```
tail       = max(VERIFY_HORIZONS + SURVIVAL_MAX_N) = 12
since_idx  = max(0, n - (tail + 1))
```

**边界为什么是 `n-tail-1` 而不是 `n-tail`**（这一条被测试和变异两边都咬过）：

窗口完整 ⇔ `i + tail <= n-1` ⇔ `i <= n-1-tail`。
所以「最后一根已定型的根」正好在 `i = n-1-tail`，而它是在**最新这一根到达的
那一刻**才刚定型的 —— 必须算进去。取 `n-tail` 会把它永远漏在「未成熟」，
表尾会一直挂着一串定不了型的结论。

| 验收 | 手段 | 结果 |
|---|---|---|
| 增量 ≡ 全量 | `test_incremental_equals_full`（表 6 与表 6b 各自逐行比） | 相同 |
| 新 K 线后该定型必须定型 | `test_new_bar_makes_the_oldest_pending_bar_settle`（按实际缺口补根数） | 通过 |
| 只算尾部 | `recompute_bars == tail + 1` | 通过 |
| 真库实测 | `backfill_kbar_survival.py --tail` | 17,654 根只重算 13 根，无告警 |

### 41.5 归因：从「被推翻」里找 t 时刻可观测的维度

`tools/probe_kbar_attribution.py`。判据是**提升量**的桶间跨度，不是命中率差。

先说当前判定层实际吃了什么：`shape.judge()` 只吃 OHLC + `vol_rel` +
`taker_buy_ratio`。**表 2 反应层、表 1.5 事件层一列都没进**，而它们全是
t 时刻可观测的。

最重要的发现：**「无」不是零信息，是两个相反群体被一个词盖住了。**

| `n_touch` | 样本 | 提升 |
|---|---:|---:|
| 6 次 | 187 | **+19.0** |
| 3~4 次 | 1,444 | +10.0 |
| 1 次 | 2,763 | +0.2 |

机制：`n_touch` 高 = 价格在密集观察线上反复触碰，被按在一个区域；

### 41.7 执行中抓到的三个真缺陷（都改了）

1. **行数校验是同义反复**。第一版 `expect = 旧行 + len(rows)`，而 `rows` 就是刚写
   进去的东西 —— 拿自己比自己永远相等，少写一根、丢一整段都拦不住。
   改成拿**表 5 应有的根数**当基准（`want_bars`）。
   变异测试「校验基准退回成 len(rows)」已能抓住。
2. **增量边界漏掉刚定型的那一根**（`n-tail` vs `n-tail-1`）。后果隐蔽：那一根本来
   只有 11 根后续，少算一次看起来结果一样；但新 K 线进来后它就该定型了，
   而边界一直排除它 —— 会**永远停在未成熟**。
3. **测试假设错**：以为「来一根新 K 线最早那个未成熟根就定型」。实际那一根只看到
   10 根，还差 2 根。改成按 `max_n - n_seen` 补足根数。

顺带记一条教训：**变异测试报「漏了」时，先确认那个变异是不是真缺陷。**
有一条「边界多退一根」我一开始当漏抓去补，算清楚才发现 `n-tail` 本来就是我写错
的边界，`n-tail-1` 才对 —— 差点为了迁就它把对的改成错的。

## 四十二、「无」拆词：实测验收（2026-11-10）

### 42.1 切分点：0 | ≥1，不选跨度最大的那个

实测「无」内部 n_touch 各档（N=1，同口径基准 68.2%）：

| n_touch | 样本 | 命中 | 提升 |
|---:|---:|---:|---:|
| 0 | 3,865 | 62.4% | **−5.8** |
| 1 | 2,763 | 68.4% | +0.2 |
| 2 | 2,104 | 72.1% | +4.0 |
| 3~ | 1,875 | 79.4% | +11.3 |

候选切分与跨度：

| 切法 | 跨度 | 结论 |
|---|---:|---|
| 0 \| ≥1 | **10.3** | **选了它** |
| ≤2 \| ≥3 | 12.8 | 跨度更大，但**放弃** |
| 0 \| 1~2 \| ≥3 | 17.0 | 留给将来升级 |

**为什么不选跨度最大的 `≤2|≥3`**：它是把 −5.8 和 +4.0 **平均掉**换来的跨度，
等于又造一个「相反群体塞进同一个词」—— 正是这次要修的病。
`0|≥1` 保住了「真空」这个负信息段的纯度：一根线都没碰到 = 真空区，
没有东西拦它；碰到了线 = 被按在线附近。

**60.2% 的根从「零信息」变成了两个方向相反、各自显著的群体。**

### 45.2 三个 z，只有一个是主口径

用户当时定的是「双 z」（`z_naive` + `z_block`）。实现过程中发现 `z_block`
不能用：它每 12 根只留 1 根，样本被砍到 **n=4**，那样的 z 一样是噪声。
实测 `恐慌盘 body_pct 小` 那格 n_block=4、z_block=−2.59，看着显著，实际毫无意义。

所以改成 **`z_cluster`（聚类稳健 / sandwich）作主口径**，`z_block` 降级为对照：

    Var(p̂) = G/(G−1) · Σ_c (Σ_{i∈c}(x_i − p̂))² / n²

去相关不能靠扔数据，要靠把方差算对。这个估计量**嵌套**朴素公式：
每根自成一簇时（G=n）修正因子≈1，方差退化成 `p̂(1−p̂)/n`。
测过：`test_cluster_z_nests_the_naive_formula`。

### 45.3 我在这套统计上错了三次

**第一次 · 块按筛选后的成员顺序切。**
`无·贴线` 占留出段 40%，拿它的成员顺序切 12 个一块，一块**实际横跨约 30 根
真实 K 线**，块内相关性被稀释 → cluster z 反而比 naive 大 1.4 倍
（`vol_rel 低于均量`：−5.53 → −8.75）。方向完全错了。
修法：按**完整时序列**里的位置算块号（`ts_index // 12`），不看筛选后的顺序。
测试 `test_cluster_blocks_come_from_real_time_not_filtered_order`。
**教训：去相关的单位是「真实时间」，不是「我手头这堆行」。**

**第二次 · 没做 G/(G−1) 小样本修正。**
G=4~5 的格子出现 cluster z 比 naive 还大（`body_pct 小`：−7.84 → −10.21）。
加修正 + 要求 **G ≥ 50**（聚类方差的相对误差约 √(2/G)：G=20 时 32%，G=50 时 20%）。
不够就报「聚类不足」，且**不进多重比较分母** —— 否则等于偷偷放宽门槛。
**教训：少簇时任何 z 都不可信，宁可报「不能测」。**

**第三次 · 以为 `lift_z_naive` 和 `lift_z_cluster` 必须数值相等。**
测试按「完全相等」写，差 0.45%，查下来不是 bug：
- `lift_z_naive` 用**零假设方差** `p0(1−p0)/n`（二项检验）
- `lift_z_cluster` 用**估计方差** `p̂(1−p̂)/n`（Wald 检验）
两者只在 `p̂ = p0` 时相等。**把它「修」成一致就等于丢掉去相关能力。**
现在有 `test_cluster_and_naive_use_different_variances` 专门钉住「它们必须不同」。

三次都是同一个模式的变体：**估计量看着能跑，方向是反的**。
所以留出集的测试全部冲着「方向」和「拒绝报数」，不冲着某个数。

| 结论词 | 留出段 n | 能否逐格推断 |
|---|---|---|
| 无·贴线 | 2,098 | ✅ |
| 插针后稳住 | 1,154 | ✅ |
| 无·真空 | 954 | ✅ |
| 插针收回 | 421 | ❌ |
| 插针 | 258 | ❌ |
| 针后远离 | 212 | ❌ |
| 恐慌盘 | 199 | ❌ 一格都验不了 |

**这印证了建集之前算过的数**：`恐慌盘` 在 30% 留出集上只有约 11 个有效样本，
远低于需要的量。这是数据量的硬限制，不是调参能解决的。

站住的几格（`无·贴线` 基准只有 6.4%）：

| 格 | n | 命中 | 倍数 | z_cluster |
|---|---|---|---|---|
| `vol_rel` 显著放量 | 448 | 16.3% | 2.5× | +5.89 |
| `vol_slot_rel` 显著放量 | 476 | 15.1% | 2.4× | +5.26 |
| `vol_rel` 低于均量 | 941 | 2.0% | 0.31× | −8.61 |
| `vol_slot_rel` 低于均量 | 969 | 3.2% | 0.50× | −5.31 |
| `body_pct` 小 | 514 | 3.1% | 0.48× | −4.49 |
| `n_touch` 密 | 727 | 10.2% | 1.6× | +3.26 |

`无·真空` 基准 2.5%：`vol_rel` 显著放量 n=73 命中 **17.8%（7 倍）z=+3.47**。

方向高度一致：**放量 → 「安静」的判断更容易失效；缩量 → 更容易成立。**
这个机制讲得通（放量说明有人在动），符合总账 §九 第 2 关。

**但没有一格能升级成判据**，三条理由：
1. 32 格过线 / 9.6 格期望，Bonferroni 后只剩 6 格 —— 多重比较的余量还在
2. 只在 3 个词上验过，另外 4 个词没数据
3. **留出集已经用掉**，再在同一段上挑维度就是在拟合留出集

结论：**留出集证明「量能方向有真信号」，没证明「某一格可以当阈值」。**
下一步要的是更多数据，不是更聪明的统计。

`judge(...)` 的 `n_touch` 入参是「无」拆成 `无·真空` / `无·贴线` 的**唯一依据**
（`shape.py` 的 `if int(n_touch) < NO_SPLIT_BY_TOUCH`），由 `build.py` 传表 1
落库值。它确实决定 label，按定义必须算判据输入。实测三分：`None → 无`、
`0 → 无·真空`、`1 → 无·贴线`。

原来的总账把它记成「判据没读」，因为 `JUDGE` 是**手写字面量**、漏了它，
而那条测试只核「文档 vs 手抄」—— 文档和手抄一起错、互相印证。

### 47.4 P2 ★ 集合改成从代码 AST 求（这是本次最重要的一条）

`tests/test_dims_ledger.py` 原来的 `JUDGE` 是手写常量，与 `shape.py`
**没有任何连接**。

**变异实测（改动前后都跑过）**：往 `judge` 里插一行 `_audit_zone = b.get("zone")`，
改动前的 `test_dims_ledger.py` **整文件 rc=0 全绿** —— 判据读了一个新维度，
台账完全没反应。

### 48.1 「能上生产」要拆成两件事：代码合格 ≠ 运行时成立

代码层面是够的：1,436 条测试全绿、前视偏差 10/10、两周期指纹一致。
但**运行时前提不成立**，五条实测：

1. **实时链路已死 8 天**。`market.db.bars` 最后一根 2026-11-01 12:56，
   当前 2026-11-09 14:35；`feed_events` 停在 2026-11-01 12:00。
2. **行情 REST 链路间歇可用，不稳定点在本地代理**。这一条我第一版写错了，
   把「间歇失败」写成了「不可达」，实测记录如下（2026-11-09 23:20 前后）：
   - 成功：`/admin/api/pack?interval=5m` 返回真实数据——`price=75182.30`、
     末根 `23:20`、距请求时刻 **0.7 分钟**、`warmup=1500` 根（满额 1500 根抓取）；
     15m 同时成功，3m 也成功（`75177.80`，末根 `23:18`）。
   - 失败：随后连试 10 次 `_fetch_klines`，**10/10** `URLError [Errno 2]
     No such file or directory`；强制直连（`ProxyHandler({})`）**3/3** 超时。
   - 原因：`urllib.request.getproxies()` 返回
     `{'http': 'http://127.0.0.1:4780', 'https': 'https://127.0.0.1:4780'}`，
     来自 Windows 注册表（`ProxyEnable=1`、`ProxyServer=127.0.0.1:4780`）。
     该端口在听（有 Established 连接），但经它出网时通时不通。
   - **正确说法**：「行情 REST 走本地代理 4780，代理/上游不稳时整条拉取就断」。
     不是「没有网络」，也不是「币安不可达」。
   - 同一进程内「pack 先成功、紧接着直接调 `_fetch_klines` 失败」这一条就足以
     证明是间歇性，不是恒定状态 —— 这也是为什么不能凭一次失败就下结论。
3. **没有增量编排器**。`build.update_verify_tail`（L1416）只刷新表 6/6b 的
   最后 `tail = max(VERIFY_HORIZONS + SURVIVAL_MAX_N)` 根，
   **不摄入新 bar、不重算其他层**。所以演化层不会自己长大。
4. **5m 原生就不在聚合器里**。`config.INTERVALS_MS` 有
   3000/15000/60000/180000/900000/…，**没有 300000**。
5. **复现性断了**。15m 的 kbar 到 2026-11-08 09:30，而本地所有库到 2026-11-01，
   且 `kbar_meta` 的 39 个键**全是参数/指纹/时间戳，没有一条记来源**。

第 5 条最该记住：**这批数据现在没法从本地任何库重放出来**。
所以在 `kbar_meta` 里登记来源之前，它只能算「一份存在过的产物」。

### 48.2 周期选择：15m 上生产，5m 只做研究视图

理由三条，都对 15m 有利：

- **只有 15m 是实时管线原生产出的**（`INTERVALS_MS` 里只有 900000）；
- **15m 历史最长**（184 天 / 17,654 根），留出集也**只在 15m 上被消耗过**；
- 5m 的留出集**从没跑过**，拿它当生产口径等于跳过预登记这一关。

反面证据也记下来，不藏：**5m 的触点样本是 15m 的 1.97 倍**
（`kbar_reaction` 47,341 vs 24,075）。这是真价值，
但价值在「样本多」，不在「能当阈值」——见 48.8。

### 48.3 两个 bug 是同一个根因

用户报的两个现象（拖动后跳回最新、悬停数据 3 秒消失）
**是同一处代码的两个后果**，不是两个 bug。

`ai_trader/web/templates/_chart_js.html`：

- L122-129 的 `dataZoom` 里 `start: Math.max(0, 100 - 12000/n), end: 100`
  是**算出来的默认值**，不是用户当前拖到的位置；
- L143 `chart.setOption({...}, true)` —— 第二个参数 `notMerge=true`，
  **整个 option 被替换**，连带销毁 dataZoom 状态和 tooltip 实例；
- L203 `pollTimer = setInterval(poll, POLL_MS)`，`POLL_MS = 3000`。

于是每个轮询周期：用户拖到第 300 根 → setOption 覆盖 → 窗口回尾部 → 跳回最新。
tooltip 同理被打断，而**轮询周期正好 3 秒**，所以用户估的「大概 3 秒」是准的。

`dash_range.html` L145-149 本来就存了 `prevOpt.dataZoom[0]`，
所以它**不跳**；但它 L195 一样每 3 秒 `setOption(..., true)`，
所以它的 tooltip 一样短命。**两处都要补，但补的东西不同。**

修法三条，缺一不可：

1. **数据没变就不重建**（`sig` 短路）。这是根治 —— 悬停期间一次都不重建。
2. **真要重建时把窗口还回去**（`zwin`，在 `datazoom` 事件里记，
   不在 setOption 里回读 —— 那会慢一拍）。只做第 1 条的话，
   来一根新 K 线就会跳回尾部。
3. **`tooltip.hideDelay = 300`**。ECharts 默认 100ms，鼠标一抖就没了。
   这管的是「离开」那一下，和第 1、2 条管的「悬停期间」是两件事。

⚠ **把轮询从 3 秒改成 6 秒不是修法**。那只是把症状周期拉长，
重建仍然会打断悬停、仍然会重置窗口。

### 48.4 总览加 5m 的边界：加的是「拉取」，不是「生产」

`ai_trader/web/live.py` L40 的 `ALLOWED_INTERVALS` 加了 `"5m": 300_000`。
它**只**决定这个只读端点能不能向币安要 5m K 线。

**没有**动 `config.INTERVALS_MS`。往里加 300000 会让实时聚合器开始往
生产 `market.db` 写 5m bar，而且要过 `market/agg.py`「3s 是原子周期」
那条断言。改聚合周期是另一件事，得单独评估下游，不能在 Web 改动里捎带。

这条边界现在有测试钉着：
`test_5m_is_not_added_to_the_aggregator_intervals`，反证过（加了就红）。

### 48.5 演化回看视图：数据结构上就把 then / post 劈开

新增三个只读端点（`ai_trader/web/kbar_api.py`，蓝图 `/admin/api/kbar`）：
`/meta`、`/evo`、`/snapshot`。

**为什么不用 `KBarStore`**：`store.py` L485 的 `__init__` 会
`os.makedirs` → `PRAGMA journal_mode=WAL` → `executescript(SCHEMA)` →
`_migrate()` → `commit()`，**它是写库的**。给核心存储层加 readonly 开关，
动的是被 1,478 条测试钉着的东西，收益不抵风险。
所以 Web 层自己开 `sqlite3.connect("file:...?mode=ro", uri=True)`，
并把「只读」用「真的去写一次必须失败」证明
（`test_readonly_connection_really_refuses_writes`），
而不是只看代码里写了 `mode=ro`——字面量写对了但没生效的情况有的是。

**为什么 then / post 必须分开**：表 6（`kbar_verify`）判决、表 6b
（`kbar_verify_survival`）存活结局、表 3（`kbar_forward`）ret1/3/5
**全是看未来才知道的**。回看视图里可以展示，但：

    then = {shape, dims, reactions, events}      # 当时就能算出来
    post = {preds, survival, forward}            # 事后才知道

这个分法是**在接口里**做的，不是在前端做的 —— 前端只是照着渲染。
理由：一旦前端拿到的是混在一起的 payload，后面任何一个改版都可能在
「顺手」中把事后字段摆进「当时」那一栏，而这种错**看起来完全正常**。
`test_snapshot_splits_then_and_post` 把两侧的键集合钉死；
`test_snapshot_post_never_leaks_into_then` 反过来查 then 里不出现事后字段名。

**结论色带只画 label**。存活结局是事后信息，画进色带就等于对
「当时发生了什么」撒谎。`tools/check_evo_ui.js` 用调色板白名单守这条，
反证过（混进非调色板颜色就红）。

**回看不轮询**。`_evo_js.html` 里没有 `setInterval`（有测试钉）。
kbar.db 是历史层，轮询只会白烧 CPU 并让 tooltip 反复重建；
而且轮询会让「数据只到某天」这件事变得更难看出来。

### 49.1 tooltip 二次修复：上一版是假修

第一次修（§48.3）加了数据签名短路，方向对，但签名里带了
`bars[最后一根].close`。实时图上最后一根是**未收盘**的那根，
它的收盘价**就是此刻现价** —— 每次轮询都在变 ⇒ 签名每轮不同 ⇒
短路**从未触发** ⇒ 每 3 秒照样 `setOption(opt, true)` ⇒ tooltip 照样被杀。

源码断言当时是绿的（`if (newsig === sig)` 确实存在、确实在 setOption 之前）。
**源码里有短路 ≠ 短路会触发**。这是本项目「测试绿只说明旧行为没坏」的又一例，
而且是我自己踩的。

现在拆两段签名：

    axisSig = cur + "|" + 根数 + "|" + 最后一根的**时间**   ← 不含收盘价
    dataSig = 最后一根的 ohlc

- 轴变了 → 全量 `setOption(fullOpt, true)`，**一根 K 线一次**
- 轴没变、只是未收盘那根在动 → 只 `setOption({series: patch})` 合并，
  **不传** tooltip / dataZoom / grid / xAxis

因为 ECharts 只在 option 里出现这些键时才去更新对应组件；不传，
tooltip 实例就不重建，悬停可以一直挂着直到你自己移开。

行为验证 `tools/check_live_tooltip.js`（Node 跑真模板 + 替身 ECharts，模拟 7 次轮询）：

    共 7 次 setOption，其中破坏性重建 2 次（首帧 + 新 K 线），
    其余 5 次都是纯 series 合并。

反证：把收盘价塞回签名 → 这条检查立刻红。第一次的假修就是在这一步暴露的。

`hideDelay` 保持 300ms，但它**不是**这个 bug 的原因 —— 它管「鼠标移开后再留多久」，
管不了「悬停期间被重建」。用户提议的「时间翻倍」数字猜对了（3s ≈ 轮询周期），
机制猜错了（没有「显示时长」这个设置）。

### 49.4 G3 增量编排器 `tools/ingest_kbar.py`

补的洞：`build.update_verify_tail()` 只刷表 6/6b 的最后 12 根，**不摄新 bar、
不重算其他层**。所以「库里多了新 K 线」不会自己传导到演化层，得手工按顺序跑
9 个 `backfill_kbar_*.py`。后果不是报错，是**静默停更**：蜡烛一直在动，
结论色带停在某一天。

设计四条：只认库里已有的 bar（不联网）；逐层往下、任一层失败就停
（演化层是链式依赖，跳过一层会让下游拿旧数据算出「看起来合理」的结论）；
**不假装全增量**；每层跑完登记来源。

三类增量语义**分开标注**，这是刻意的：

| 类别 | 层 | 增量来源 |
|---|---|---|
| `INPUT_INCREMENTAL` | lines, facts | 输入被裁剪（只喂新 bar），函数本身无 since_ts |
| `INCREMENTAL` | verify, survival, dims | 函数内部有 `since_ts` |
| `FULL_REBUILD` | reactions, events, forward, shape | 只有 `rebuild` 开关，整表重算 |

混成一个「增量」说法，运维就会以为「标了增量就一定快」。

`--from-1m` 走自写的 `_agg_from_1m`，**不用** `build.load_1m_as_15m` ——
那个函数查的表叫 `klines`，而 `data/market.db` 里没有这张表（实测只有
`bar_gaps` / `bars` / `feed_events`），直接
`sqlite3.OperationalError: no such table: klines`。

实测：15m 无新 bar（见 49.5）；5m `--from-1m` 聚合出 255 根、新增 28 根。

### 50.4 结论筛选（点图例里的「插针」）

用户要求的功能：点图例里的「插针」→ 只看插针那些根。

**为什么不用 ECharts 内置 legend**：legend 只能整条 series 显隐，
而这里要的是「逐个数据点设透明度」—— 保留选中类 + 前后各 N 根上下文。
legend 表达不了「保留上下文」这个语义，所以用 HTML chip。

**为什么必须保留上下文（CONTEXT = 3）**：这是这个功能的**立意**所在。
插针本身不是信息，插针**前后**的价格反应才是 —— 这正是
「观察线不是支撑线，要看价格在它上面的反应」这句定位的操作化。
只留插针那几根，等于把要看的东西掐掉一半。

实现三处：

1. `focusMask(labels, picked, ctx)` —— 纯函数，算「哪些下标该亮」。
   `picked` 为空 → 返回 `null`（全亮）；选中词在本周期一根都没有
   → 也返回 `null`（**不能全暗**，那看着像图坏了，而且换周期后很容易撞上）。
2. `render()` 里按掩码给三处数据点设透明度：K 线 `itemStyle.opacity`、
   结论色块 `st.opacity`、观察线反应散点 `pt.itemStyle.opacity`。
   未筛选时保持纯数组形态（ECharts 走快路径，旧行为一模一样）。
3. `renderChips()` 画 chip，带**该结论的根数**。为什么带数字：
   7 个词样本量差很远（15m 里「无·贴线」6,768 根、「恐慌盘」437 根），
   不写数字，用户点进去看到零星几根会以为筛选坏了。

chip 点击是纯前端就地重绘，不重新请求 —— 筛选是视图状态，
让后端为「我怎么看」再算一遍是浪费，而且会闪。

### 51.8 「两周期是否同口径」这个检查，我自己错了两次

这一节专门记错，因为两次错都出在**同一个毛病上：猜键名**。

**第一版**：取 `json.loads(value)["hash"]`。除了 `shape_params`，
其余各层根本没有 `hash` 这个键 → 全部打印成 `"?"`，
我却按「两周期都是 `?`，所以相同」判了 OK。**这是假绿。**

**第二版**：按层猜键名（`line_params_hash` / `verify_hash` /
`survival_hash` / `dims_hash` / `params_hash`）→ 除 shape 外全部
「(无指纹字段)」，于是判成「8 层不同口径，需重跑」。**这是假红。**

**真相**：只有 `shape_params` 带指纹字段（`params_hash`）。
其余各层是**把当时的参数值原样存进 JSON**（`thresholds`、`tol_pts`、
`horizons`、`count_cuts`、`touch_tol_pct` …）。那比指纹更好 ——
指纹只能证「同不同」，存值能证「同在哪、不同在哪」。

**正确判据**：把两个周期的 params JSON 去掉 `interval_label` /
`interval_ms`（这两项本来就该不同）后逐字段比。结果：

    OK line_params         9 个字段完全一致
    ✗ facts_params         2 处不同: slots_per_day / ticks_per_bar
    OK reaction_params    12 个字段完全一致
    OK event_params       17 个字段完全一致
    OK forward_params     16 个字段完全一致
    OK shape_params       13 个字段完全一致（指纹 9d23fff74ad3 相同）
    OK verify_params       4 个字段完全一致
    OK survival_params     4 个字段完全一致
    OK dims_params         5 个字段完全一致

那 2 处「不同」也是正常的 —— 它们是**周期的函数，不是可调口径**：

    5m  slots_per_day = 86400000/300000 = 288，ticks_per_bar = 300000/3000 = 100
    15m slots_per_day = 86400000/900000 =  96，ticks_per_bar = 900000/3000 = 300

库里的值与公式逐一核对，**四个数全对**。

所以结论是：**9 层全部同口径**，两周期可以按同一套阈值解读；不可横比的
仍然只有 D-24（绝对点数阈值）和 D-25（区间库来源），跟这次无关。

教训：**验证脚本自己也会撒谎。** 打印出 `?` 的时候，那不是「值相同」，
也不是「库坏了」，是**你在问一个不存在的问题**。宁可把 JSON 的顶层键
整个 dump 出来看一眼，也不要按记忆猜字段名。

### 51.10 一个测试数量「掉了 28 个」的假警报

收尾时跑全量测试，从部署前的 1,531 passed 变成 1,503 passed，少了 28 个。
看起来像删坏了测试。查下来是**虚惊**，但原因值得记：

`tests/test_deploy_lf_only.py` 里有

    SHELL_DIRS = ('deploy', 'tools')

    @pytest.mark.parametrize('path', _shell_files())
    def test_no_crlf_in_shell_scripts(path):

也就是说**`tools/` 下每一个 `.sh` 都会长出一个测试**。
本轮为了部署临时写了 28 个 `tools/_*.sh`（全部用 LF 写的，
所以这 28 个测试一直是绿的），删掉它们，测试数自然就回到真值。

核对：1,503 = 部署前基线 1,498 + 本轮新增
`tests/test_kbar_csv_volume.py` 的 5 条。**一分不差。**

顺带确认两件事：`git ls-files tools/*.sh` 是空的（`tools/` 里
本来就没有被跟踪的 shell 脚本，我删的全是自己写的临时件）；
`deploy/` 下 4 个脚本都在，`git status` 无任何删除行。

**教训**：看到「测试变少了」先别当成删坏了 ——
这套测试里有**按目录内容参数化**的用例，工作区里放临时文件
会让计数虚高。判断基线对不对，要拿「上次真实基线的构成」去对，
不是拿「上次跑出来的数字」去对。
