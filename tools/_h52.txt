## 六点五十二、第一笔真实交易的路径：补测引擎自主开仓，抓出 `trade_close` 漏写 qty

### 一、覆盖缺口在哪

项目已有很扎实的两层 e2e，但实盘排练开仓是这样写的：

```python
sig  = eng.trend.want_entry(PX)          # 手动问信号
plan = eng._trend_plan(PX, 100.0, sig)   # 手动算计划
await eng._open(sig, plan, ...)          # 手动下单
```

三段各自都测了，但**「引擎自己在 `_step` 里决定要不要开仓」这段编排没测过**。而这段编排是有内容的：闸门顺序、本根 4h 已熔断不许重开、下单失败退避、权益过期拒绝入场。真实运行时，第一笔交易正是这条路产生的。

### 二、新测试：让引擎自己开仓、自己平仓

不 mock 引擎内部任何一步，只喂真实 4h K 线 + 真实 HTTP + 严格假币安：

| 测试 | 验证什么 |
|---|---|
| `test_engine_opens_the_first_trade_by_itself` | 调 `_step` 自己开出第一笔，只开一笔，持仓与库都有记录 |
| `test_engine_does_not_open_twice` | 连续再跑 5 轮不许重复开仓（趋势 1x 满仓，重复买入直接击穿杠杆） |
| `test_engine_closes_by_itself_and_settles` | 价格下穿均线后自己平仓，盈亏正确结算落库 |

### 三、第三条测试当场抓到一个真缺陷

按 `(出场-入场)*数量` 算毛利，和库里对不上：**我算 −9.95004，库里 −9.93**。

先把数值全打出来，不猜：

```
卖单实际发出   0.00331        （已按 step=0.00001 向下取整）
账户剩         0.00000668 BTC （卖不掉的粉尘）
pnl_gross    = -9.93          ← 用实卖量 0.00331 算的，正确
qty          = 0.00331668     ← 这是【持仓量】，不是实卖量
```

同一个变量 `sold_qty` 不可能两个值。查到写入端：

```python
UPDATE trades SET exit_ts=?, exit_price=?, pnl_gross=?, fee=?, ...
                                        ^^^ 没有 qty
```

**`trade_close` 的 UPDATE 漏了 `qty` 列。** 引擎在 `_close` 里明确传了 `qty=sold_qty`，写入端把它丢了——参数白传。

反证一次：会不会有意保留买入量？注释只说「更新而不是插入」，没提 qty；引擎端明确传 `sold_qty`。**纯漏写，不是设计。**

后果不只是难看——这张表内部自相矛盾：`pnl_gross` 用实卖量算，`qty` 却是持仓量。任何人拿 `(exit-entry)*qty` 重算都会得到 −9.95004，与库里的 −9.93 冲突。**而这类重算是所有绩效分析的入口。**

修好后：库里 `qty = 0.00331`，与 `pnl_gross` 完全自洽。

```
变异（删掉 qty=?）-> 断言失败：
  「落库数量 0.00331668 不是 step 向下取整后的成交量 0.00331000」
```

### 四、历史数据没有被污染

线上已平仓 4 条，逐条用 `(exit-entry)*qty` 复算，**全部 0 偏差**。原因：那 4 笔是永续剥头皮仓（step=0.001），持仓量与卖出量本来就相等。缺陷只在现货显现——买入手续费扣在 BTC 上，实际到账比计划少。

### 五、一次差点误报

毛利对不上时我第一反应是「记账算错了」。实际是两件事叠在一起：

1. 我默认持仓量 == 卖出量（错的，现货必然有 step 残留）
2. 代码确实漏写了 qty（真的）

> 如果当时直接改代码去「修」毛利算法，就会把正确的东西改坏。是先把数值全打出来，才分清哪一半是真缺陷。

### 六、顺带确认：粉尘的钱不会消失

`equity()` 把粉尘市值算进权益，而 `position()` 对粉尘按空仓处理（可交易性）——两个职责分开，都正确。测试里加断言锁住这条不变量：`权益 == USDT 余额 + 粉尘市值`，否则每笔交易吞一点，账户会缓慢漏血且无任何记录。
