## 六点一百三十一、唐奇安真的上线了：三次线上翻车与修法（2026-11-02 下午）

> 六点一百三十 写的是"唐奇安可上线"。这一条写的是**把它真的跑起来时踩到的三个坑**。
> 三个坑全部是「代码看起来对、单元测试全绿、线上静默失效」那一族。

### 一、坑 1：写了但没落地（AI_EXEC_MARKET）

我把 AI_EXEC_MARKET=perp 写进 /etc/ai-trader/env，脚本还打印了
AI_EXEC_MARKET = perp 作为验证。**然后 grep 文件，这一行根本不存在。**

根因（部署脚本）：

    want = {"AI_STRATEGY":..., "AI_EXEC_MARKET":"perp", ...}
    for k, v in want.items():
        d[k] = v            # 写进了内存字典
    lines = ["%s=%s" % (k, d[k]) for k in order]   # order 来自【原文件】

order 只包含原文件已有的键。AI_EXEC_MARKET 原本不在文件里，于是它进了 d
却没进 order，写盘时被丢掉。而我的"验证"读的是 d——**验证手段本身在撒谎**，
这正是项目里反复出现的那一族缺陷。

后果：引擎以为自己在做现货，于是 _qty_step 返回 0.00001（永续是 0.001）、
_min_notional 返回 5（永续是 50/55）、费缓冲 0.3%（永续 0.1%）。
纸面上算出 plan_qty=0.00091 这种**永续交易所会直接拒单**的数量。

修法：if k not in order: order.append(k)，并且**验证必须回读文件**，不读内存：

    back = {k: v for line in open(p) ...}
    bad = [k for k, v in want.items() if back.get(k) != v]

### 二、坑 2：唐奇安上线当晚每 3 秒崩一次（KeyError）

部署后服务 active、看板有数据、日志一切正常。真实情况是：

    2026-11-02 16:08:03 ERROR 决策步骤异常
    File "engine.py", line 964, in _step_trend
        sig_key = "watch|%s|%d" % (st["above"], int(st["sma"] or 0))
    KeyError: 'above'

唐奇安的 state() 没有 above / sma 这两个键（它有 above_upper / upper）。
_step_trend 里三处还在用趋势版的键名。异常被上层 except 吞成一行
「决策步骤异常」——**服务活着，引擎从来没评估过一次**。

最刺眼的是：我在写 donchian.py 的测试 docstring 时【预言过】这个故障，
然后照样把它发布出去了。当时 12 个用例全绿，因为它们全在策略内部，
没有一条真的跑 _step_trend。

修法不是到处加 .get(默认值)——那会把"没这个字段"悄悄变成 0/False，
策略于是拿一个假的上轨做判断，更坏。修法是**一处归一化**：

    def _chan_view(self, st):
        """把两个策略的 state() 归一化成决策分支认识的字段。"""
        if not self._is_donchian():
            return st                      # 趋势版原样返回（同一个对象）
        out = dict(st)
        out["lookback"] = st.get("entry_n", 0)
        out["sma"]      = st.get("upper")
        out["above"]    = bool(st.get("above_upper"))
        out["exit_above"] = not bool(st.get("below_lower"))

### 三、坑 3：体检报告说"可以切 live"，而实际开不出仓

tools/preflight_live.py 有两个独立缺陷：

1. **check_exchange 永远构造 SpotExecutor**，与 exec_market 无关。
   切到永续之后跑体检，查的是现货钱包余额和现货交易对规则——
   结论一本正经，和真实下单那条路径毫无关系。
2. **spec["base"] KeyError**：LiveExecutor.spec() 少 base / quote 两个键，
   而 SpotExecutor.spec() 有。体检跑到「资金」一节直接崩，
   而前面每一节都显示 GO——看起来像"几乎通过"。

修法：按 exec_market 选执行器；live.spec() 补齐 base / quote；
「够不够开一手」的门槛从 spec["min_notional"] 改成
max(min_qty * px, min_notional)。

最后一条是本轮最有价值的检查。永续 BTCUSDT：minNotional=50，但
minQty=0.001 手 = 78.2U。**只比 minNotional 会得出"100U 很宽裕"，
实际一手吃掉 78% 权益。** 这就是纸面账户 71.77U 时每轮空转、
而体检全 GO 的原因。

### 四、纸面账户纪元切换（这是必须的，不是擦亏损）

旧纸面余额 71.77029U，来自 4 笔【现货 3s 剥头皮】交易（-20.46U）。
两个理由必须重置：

1. 那本账算的是现货口径，而现在做的是永续；把现货账本当永续起点没有意义。
2. 更硬的：**71.77U 在永续口径下一手都买不起（78.10U）**。留着旧余额，
   新策略连一次决策都走不到，系统会永久停在"资金不足"——
   那不是验证，是结构性不可操作。

做法：executor_state.balance -> 100.0、清空 engine_state.block_bar、
写一条 journal（kind=epoch）留痕。**trades 表一条未删**，审计链完整。
用户已向合约账户转入 100 USDT，纸面账本对齐这个数字才有意义。

### 五、改掉了第三条会撒谎的日志

    决策引擎已挂载：mode=paper 策略=donchian 权益=100.00U

这一行打印的是 _last_equity or paper_balance。第一次循环还没跑，
_last_equity 是 None，于是**永远打印配置值 100**，而执行器实际从库里
恢复的是 71.77U。运维看到"权益=100"会以为钱够，而引擎每一轮都在
"资金不足"里空转。改成读执行器真实余额：

    决策引擎已挂载：mode=paper 策略=donchian 执行器余额=100.00U 品种=perp

### 七、回撤余量为什么保持 WARN 而不是升级成硬阻断

我先把它升级成 NO-GO，然后反证了一下，发现不成立：

- 100U + BTC 一手满仓的回测（7.15 年真实账户口径）最终 168U、
  最大回撤 24.4%，**它没有永久停摆**——权益总在下一笔进场前回到门槛之上。
- 真正"连一手都开不出"的处境，「按当前权益的实际计划」那一项已经报 BAD。

所以语义是"能交易，但一轮正常回撤就可能卡住"= 提醒，不是阻断。
把提醒当阻断，等于给一个能跑的策略判死刑。
（三个既有测试也明确锁定了 WARN 语义，它们是对的。）
