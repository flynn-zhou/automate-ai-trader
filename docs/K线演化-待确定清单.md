## 二、第 3 步新出现的（反应层）

### D-5 「碰到」的判据（`touch`）

> **2026-11-08 补实测分布**（17,654 根 × 17 线 = 228,718 个可评估对，其中碰到 24,075 对）：
>
> | 容差 | 会额外收进来的 (根,线) 对 | 占可评估 |
> |---|---|---|
> | `<=0.01%` | 2,429 | 1.06% |
> | `<=0.05%` | 12,343 | 5.40% |
> | `<=0.1%` | 24,789 | 10.84% |
> | `<=0.3%` | 67,559 | 29.54% |
> | `<=1%` | 144,264 | 63.08% |
>
> 现在 `TOUCH_TOL_PCT = 0.0`（严格：`l <= p <= h`）。容差每放宽一档，
> 「碰到」的定义就换一次，**表 2 的行数会随之变化，进而改掉表 3 的 held**。
> 所以这不是一个可以随手调的参数，是要你定的事。
>
> 现实例子（就是这次被问到的两根）：
> - 2026-11-07 15:45 UTC（北京 23:45）：`prior_low@15m` 线价 75,786.8，本根最高 75,778.3 → **差 8.5 点（0.0112%）没碰到**
> - 2026-11-07 21:15 UTC（北京 05:15）：`prior_low@15m` 线价 75,571.6，本根最低 75,575.9 → **差 4.3 点（0.0057%）没碰到**
>
> 这两根都是「差一点点」。设 0.02% 容差，第 2 根就会多出两条触碰；
> 设 0 就都没有。**两种都说得通，但对「这一根的读数」影响很大。**

表 2 的入表条件是 `touch=1`，但设计稿没定义什么算碰到。

| | |
|---|---|
| 临时做法 | **无阈值**：`l <= line_price <= h`（这根 K 的价格区间覆盖了线价，含边界）。这是纯事实 |
| 备选 | 加容差（例如 `dist_pct` 绝对值 ≤ 0.1% 也算碰到）。加了就是阈值，会把「差一点」也算进来 |
| 影响 | 判据松一点，表 2 行数暴涨，`nth_touch` 全乱；紧一点会漏掉「插一下就回」的情形 |
| 我的倾向 | 用无阈值版，**同时把「差一点」的程度用 `dist_pct` 留着**，需要时按分位数再切 —— 先不预设 |

### D-6 `side`（从上方来 / 从下方来）用哪个基准

| | |
|---|---|
| 临时做法 | 用**本根开盘价** `o` 与线价比：`o > p` → `from_above`，否则 `from_below` |
| 备选 | 用**上一根收盘价** `c[-1]` 比。差别出现在跳空/换段那几根 |
| 影响 | `pen_depth_pct` / `recover_pct` 的公式按 `side` 分支，**选错会让这两个数整体反号** |
| 备注 | 用开盘价的好处是「只用本根自己的信息」，不受上一根是否缺数据影响 |

| | |

## 四、第 3 步交叉核对时发现的（D-14）

### D-14 线「消失」之后，反应还能不能用它

这一条是第 3 步做完**交叉核对时发现缺陷**才浮现的，不是设计稿里写清的。

| | |
|---|---|
| 现象 | 区间演化在 `PRE` 段（区间未成形，四线全空）时，表 0 就不落 range 线行。第一版取「最近一个就绪值」，会把消失之前的线**无限期往前带** —— 实测 2026-08-05 01:00 转 PRE，而 05:15 的 K 线仍在拿 02:00 的 `range_key` 判「碰到」 |
| 已实现（按证据定的） | **只取「上一根 K 线」那一行；那根没有这条线，就是不存在**，不往前带。依据：表 0 对每条存在的线在每根 K 线上都无条件落行，「缺行」= 「不存在」 |
| 为什么这也自动满足「防偷未来」 | 15m 根 `t-15m` 的收盘时刻**正好就是** `t` 的开盘时刻，那一行用到的信息与本根开盘时完全一样 |
| 影响 | 表 2 从 24,577 行降到 24,075 行，少掉的 574 行全是 range 线；15 条同周期线一行未变 |
| 丢弃计数 | `line_absent_at_prev_bar` 71,313（与 `line_not_ready` 17 分开计，前者是「曾经有、现在没了」） |
| **要你确认的** | 是不是同意「线消失期间不做反应」。另一种可能的读法是：线消失不代表价格不在那个位置，可以继续拿最后一个已知值观察。**两种都和「不碰判断标准」不冲突，但会改变表 2 的行数** |
| 决定后要改 | `reaction.py::pick_prev` + `store.line_series` + 回填重跑 + 探针 |

### D-17 `neutral` 只做了「没碰到任何线」这一半

| | |
|---|---|
| §8.2 的完整定义 | 「没碰到任何观察线、**量正常**、**在空间中间**」 |
| 现在做的 | 只用了「本根没有任何事件、且表 2 里没碰到任何线」→ `state = neutral`。后两项都要阈值（量正常 = 相对成交量多少算正常；空间中间 = 距上下沿多远算中间），属于第 6 步的判断标准 |
| 三态覆盖 | 有事件 7,328 根（41.5%）/ 有接触无事件 4,236 根（24.0%）/ `neutral` 6,090 根（34.5%）—— 三态之外没有漏网的根，探针逐条查过 |
| 为什么不硬填 | 「有接触无事件」那一类（24%）留空是有意的：它既不是「没意义」（它碰到了线），也不能编个事件。硬贴标签正是 §8.2 禁止的 |
| 决定后要改 | 加两个阈值 → `neutral` 会缩小，「有接触无事件」的一部分要重新分；`event.py::build_events` 的 neutral 段 |

### D-18 反包与「当根的反向突破」要不要都记

| | |
|---|---|

## 七之三、D-23：事后看多远，以及「无」要不要拆

D-23 是 2026-11-10 用户问「事后是多事后、最多多少根、最少多少根、有没有实时跟随」
之后测出来的三件事。**三件都已有结论**：前两件按数据定，第三件用户当场拍板拆词。

### D-23.1 事后窗口：已按实测定下来（不是拍的）

| 项 | 值 | 依据 |
|---|---|---|
| 最少几根开始判 | **1 根** | 下一根收盘就能给出裁决 |
| 实测定型分布 | N=1 45.5%、N=2 64.0%、N=3 75.0%、N=6 90.2%、N=12 100% | 17,654 根逐根算「裁决在第几根之后不再变」 |
| 中位 / p90 / p99 | **2 根 / 6 根 / 11 根** | 同上 |
| 本层截断 `SURVIVAL_MAX_N` | **12 根** | p99 = 11；测到 12 时还在以 1.0%/档 下降，是**截断不是自然终点**。换周期/品种必须重测 |
| 原 `VERIFY_HORIZONS=(1,3)` | 保留，但**不再当主口径** | N=3 只覆盖 75%，剩下 25% 时还是临时答案 |

**为什么固定 N 是错的表达**：裁决随 N 单调（窗口越长越可能破极值，破了不会变回），
所以每根都有一个「第一次被推翻」的根数。这个数比分档裁决信息量大，而且修掉一个
结构性偏差：

- 守住型（`must_hold=True`）在短 N 下**偏松** —— 还没来得及破就算成立
- 会破型（`must_hold=False`）在短 N 下**偏严** —— 还没来得及破就算推翻

两类预言放在同一个 N 上比命中率，本身就不成立。所以新增表 6b（见 D-23.3）。

### D-23.2 实时跟随：已经做了

原来表 6 是**全量重写**（每次先 `delete_verify(horizon)` 全删再全插），
没有任何增量路径 —— 用户问「做到了吗」，答案是没做到。

现在 `build.update_verify_tail()` 只重算尾部：

| 项 | 做法 |
|---|---|
| 为什么要增量 | 行只依赖 `bars[i+1..i+N]`；窗口一旦落进历史就固定了，重算必然同结果 |
| 边界 | `since_idx = n - (tail + 1)`，`tail = max(N, SURVIVAL_MAX_N) = 12` |
| 边界为什么是 `n-tail-1` 不是 `n-tail` | 窗口完整 ⇔ `i <= n-1-tail`，所以**刚定型的那一根正好在 `n-1-tail`**，它是在最新一根到达那一刻才定型的，必须算进去。取 `n-tail` 会把它永远漏在「未成熟」 |
| 验收 | `test_incremental_equals_full`（增量逐行 ≡ 全量）+ `test_new_bar_makes_the_oldest_pending_bar_settle`（补足缺口后该定型必须定型） |
| 真库实测 | 17,654 根里只重算 13 根，行数对得上，无告警 |

### D-23.3 表 6b `kbar_verify_survival`：新维度（已经加了）

一根一个答案，粒度与表 6 的 `(ts, horizon)` 不同，所以另开一张表；
`survival_hash = b6da1717a9cc` **故意与 `verify_hash` 分开** ——
并进 `verify_params()` 会改掉表 6 的指纹、全库立刻变「过期」。

三态必须分开，这是本层最要紧的地方：

| 状态 | 含义 | `break_n` |
|---|---|---|
| `已破` | 第几根被打脸/被证实，**定型** | 有值 |
| `活到最后` | 满 `max_n` 根都没破，**看完了** | NULL |
| `未成熟` | 后面的根不够 `max_n`，**还没看完** | NULL |

⚠ `未成熟` 与 `活到最后` 的 `break_n` **都是 NULL**。只按 NULL 统计会把表尾
「还没验」算成「验完了没破」，命中率凭空变好。`status` 列就是防这个的，
`survival_counts()` 也只把「已破 + 活到最后」算 `settled`。

### D-24 绝对点数阈值能不能跨周期用？—— **不能横比，暂不缩放**

**口子在哪儿**：`shape.py` 里两个阈值是**绝对点数**，不是比例：

    WICK_PTS_MIN = 40.0          # 影线至少 40 点才算针
    SCENARIO_TOL_PTS = 20.0      # 场景容差 20 点

随机游走下，价格的波动幅度大致按 **√时间** 增长。所以同样「一根影线」，
5m 的点数天然比 15m 短。同一个 40 点门槛，在 5m 上**更难过**。

**实测（2026-11-11，两套周期同一份判据）**：

| 结论词 | 5m 占比 | 15m 占比 | 方向 |
|---|---|---|---|
| 插针 | 3.61% | 4.88% | 5m 更少 ← 与「5m 影线更短」一致 |
| 恐慌盘 | 4.08% | 2.48% | 5m 更多 ← `vol_rel` 是相对的，5m 把突发隔离在单根 |

**所以**：

1. **同一周期内纵向比**是合法的（阈值没变，样本口径一致）。
2. **跨周期横比「插针」「恐慌盘」的计数是不合法的** —— 差异里混着阈值效应，
   分不清是市场不同还是口径不同。
3. 要横比就得让 `WICK_PTS_MIN` 随周期缩放（比如按 √时间），
   但那是**改判据**，用户明确说过「先不调阈值」「该用多少用多少」。
   **这一轮不动。**

**谁在等这个决定**：想拿 5m 与 15m 的着针率做对比的时候。
**影响字段**：`kbar_shape.pin_kind` / `label`、`kbar_verify` 的每个 verdict。

### D-25 `market_range.db` 已经丢了，两个周期用的**不是同一份**区间库

**事实**：仓库里 `data/market_range.db` **不存在**了，只剩
`tests/fixtures/range_v11_reference.db`（192 KB 测试夹具，1,439 根 1h）。
它是表 0 区间四线唯一的来源，没有它就没有「区间位置」这一整类维度。

**怎么救的**：币安 API 不通（`WinError 10054`），走离线 ——
`data/range_bars_15m.csv`（17,280 根 15m，2026-05-08 → 11-04）→
`engine.load_1h()` → `engine.build()` → `persist_run()`，
写到**独立文件** `data/market_range_rebuilt.db`。

**为什么写独立文件名，不补回 `market_range.db`**：
一旦那个名字重新出现，以后谁重跑 15m 就会拿到一套新算的区间线，
与已落库的 15m 结果不一致，**而且不会有任何报错**。名字分开，要用就
显式 `--range-db` 指过去。

#### 保真度：原来说的「88.1%」不可复现，实测是下面这三个数

旧版本这里写「抽 600 小时，1400/1590 = 88.1%，剩下 12% 未归因」。
**这个数复现不出来**，而且当时的对账口径有 bug（见下）。2026-11 审计
用**两库各自的 `ts`（UTC 毫秒）**重算，结果分三层：

| 比对 | 口径 | 结果 |
|---|---|---|
| 夹具 `range_bars` vs 重建库 `range_evolution` | 1,439 个共同小时，格级只比两边非空 | **3,732/3,989 = 93.56%** |
| 同上，只看**分歧结束之后**的 1,343 小时 | 同上 | **3,732/3,732 = 100.00%** |
| 5m 落库 `range_*` vs 重建库 | 按 `src_ts` 取同一小时，13,645 格 | **100.00%**，0 格不同 |
| 15m 落库 `range_*` vs 重建库 | 同上，10,049 格可比 | **96.19%**，383 格不同 |

**那 3.56% 的分歧不是「未归因的随机偏差」，是预热窗口**：分歧全部落在
`2026-09-05 15:00 ~ 2026-09-09 11:00`（北京）这 91 个小时里，之后
**逐格 100% 一致**。夹具是从老项目生产库里导出的，它在窗口开头那几根
的区间状态是**上一段历史带过来的**；重建库从 CSV 冷启动，前
`WARMUP_1H_BARS=600` 根是在没有前置状态的条件下自己长出来的。
区间引擎是**状态机**（同一小时的四线取决于它前面那条区间怎么生的），
所以冷启动窗口内必然不同、窗口外必然收敛。**这不是缺陷，是初值差异。**

#### 真正的结论：两个周期的区间维度不可横比

5m 落库行对上重建库是 **100.00%**，说明 **5m 是用重建库建的**；
15m 是 **96.19%**，说明 **15m 用的是那份已经丢了的原库**。两者差异
（383 格）里：

- 380 格在夹具可验证窗口**之外**（其中 99 个小时在夹具起点之前、
  1 个小时在重建库末尾之后 —— 15m 的 `src_ts` 最新到 `2026-11-08 06:00`，
  重建库只到 `2026-11-04 11:00`，这 1 小时根本无从比对）；
- 0 格落在**夹具可验证窗口之内**：在夹具覆盖的 1,439 小时里，
  15m 落库值与重建库 **6,847/6,847 = 100.00% 一致**。

> ⚠ 所以修正一条早先的说法：**不能说「两周期区间线没有任何不一致」。**
> 准确说法是：**在能验证的范围内（夹具覆盖段）两者一致；在不能验证的
> 范围内（原库已丢），15m 与 5m 的区间四线来源不同，不可横比。**
> 这直接限制了任何「拿 5m 和 15m 的 `zone`/`direction`/`nth_touch` 做对比」
> 的结论 —— 差异里有一部分是**数据源不同**，不是周期不同。

**谁在等这个决定**：
1. 要不要拉历史区间库（需要网络），把 15m 也统一到可验证的来源；
2. 在此之前，**5m 与 15m 的 `空` 类维度（`zone`/`direction`/`range_ts_h`/
   `fam`/`seg`/`seg_idx`/`nth_touch`）一律不许跨周期横比**；
3. 15m 要不要也用重建版（**不建议** —— 会动已经落好的 17,654 根，
   而且改动后 15m 的区间维度会整体偏移，等于换了一套数据）。

**影响字段**：表 0 的 `range_*`、表 1 的 `zone`/`direction`/`range_ts_h`/`fam`/`seg`/`seg_idx`、
表 2 的 `nth_touch`（按 `(fam, seg, line_key)` 数，换段就会重数）。

> 口径提醒（这条坑踩过三次）：两个库的 `ts_h` **一个是北京时区字符串、
> 一个是 UTC**（夹具 `ts=1788580800000 → ts_h='2026-09-05 12:00'`，
> 而该 ts 的 UTC 是 `04:00`）。**对账一律用 `ts`，绝不能用 `ts_h` 或
> 手写格式化时间**，否则会得到一堆假的「分歧」。

## 七之四、D-26：演化层不会自己长大（没有增量编排器）

### D-26 演化数据停在某个时刻，而且**来源没登记**

现象（2026-11-09 实测）：15m 的 `kbar_shape` 到 **2026-11-08 09:30**，

1. **来源没登记**。`kbar_meta` 的 39 个键全是参数/指纹/时间戳
   （`params_hash` / `dims_hash` / `verify_hash` / `survival_hash` /
   `split_hash` / 各层 built_at / 计数），**没有一条记「这批数据是从哪个库、
   哪段区间、用什么命令建的」**。所以复现断了以后，没有线索能接回去。
2. **没有增量摄入**。`build.update_verify_tail`（L1416）只重算表 6/6b 的
   最后 `tail = max(VERIFY_HORIZONS + SURVIVAL_MAX_N)` 根，
   **不读新 bar、不重算表 0/1/2/3/5/7**。要让演化层往前长，
   现在只能整周期重跑 `build_and_persist`。
3. **实时链路本身是死的**（`feed_events` 停在 2026-11-01 12:00，
   币安 REST 不可达），所以就算有摄入器，也没有新数据可摄。

**要定的事**（下次动这块之前先定，别边做边想）：
