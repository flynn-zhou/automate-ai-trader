## 六点五十一、量出「3 秒系统实际跑 6 秒」——假的；顺带抓到测试的第二个假通过

### 一、起因

看板宣称 3 秒实时。量引擎循环节拍（取 `equity` 表相邻两行 `ts` 的差）：

```
最小 6.0 秒   中位 6.0 秒   P90 7.0 秒   平均 6.4 秒
99.7% 的间隔超过 5 秒 —— 从来没有出现过 3 秒
```

这个信号太像「丢掉一半决策」了：`_on_bar` 确实有一条「上一轮还没跑完，丢弃本轮」的锁保护。若单轮 `_step` 要 5~6 秒，正好丢掉一半 3 秒桶。

往下追了一串，全部排除：

| 假设 | 实测 |
|---|---|
| `_step` 慢 | 本地 0.1 毫秒 |
| 服务器资源不足 | 负载 0.02，CPU 0.2% |
| WS 批量到达 | 逐条 `async for`，无批处理 |
| 聚合器一次闭合多根 | 一次恰好 1 根 |
| 写入队列阻塞 | maxsize=10 万 |

### 二、根因：我拿被节流过的表推断上游节奏

```python
def log_equity(self, e):
    """同秒去重，避免 3s 循环把权益表写爆。"""
    now_s = int(time.time())
    if now_s - self._last_equity_s < 5:
        return
```

**权益表是 5 秒节流写入的。5 秒在 3 秒粒度上取整，就是 6 秒。**

真实循环正常：3s 桶最近 30 分钟 **597/600 根**，596 个间隔里 **595 个严格等于 3.000 秒**，只有 1 个 6 秒缺口（一次聚合边界）。数据管线健康。

> 教训：**被节流过的表不能用来推断上游节奏。**
> 而且 docstring 写的是「同秒去重」，代码实际是 5 秒——名不副实的注释正是把我带偏的帮凶。

已改成 `EQUITY_MIN_GAP_S = 5`，docstring 说清是 5 秒节流，并把这次测量错误本身写进注释。

### 三、测试的第二个「通过的理由是错的」

给节流写了 3 条测试，全过。变异检查（把节流改成恒不生效）——**依然全绿**。

原因：`equity` 表是 `ts INTEGER PRIMARY KEY`，写入用 `INSERT OR REPLACE`。测试每次 `int(time.time()*1000)`，6 次快连调用落在**同一毫秒**，主键相同 → 6 条合并成 1 行。断言 `n == 1` 通过，是因为**主键合并**，不是因为节流。

修法：每次调用给不同的 `ts`。重做变异，这次是干净的断言失败：

```
AssertionError: 写入了 6 行（应为 1）
assert 6 == 1
```

> 顺手把固定 `sleep` 换成轮询等待——0.4 秒等不到单写入队列落盘，这是最初那次 `0 == 1` 失败的原因。

### 四、顺便排除的两个假设

1. 以为 `spot.market_order` 会把 `reduce_only` 传进现货请求（现货不支持，会被拒单）。**查代码：根本没传。**
2. 以为请求没指定 `newOrderRespType`，默认 `ACK` 会让响应缺 `executedQty`，把「已成交」误报成「未成交」——那比手续费算错严重得多。**查币安官方文档：MARKET 和 LIMIT 默认就是 `FULL`。** 假设不成立，未改。

### 五、验证

**261 个测试全绿**（新增 3 条），358 个脚本语法正确，变异检查产出真实断言失败（`assert 6 == 1`，非语法错误）。
